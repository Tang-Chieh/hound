Executive Summary

The Hound security team conducted this comprehensive audit of the USSD protocol, focusing on its collateral-backed stablecoin issuance, oracle integrations, rebalancing controls, and Uniswap-based execution paths.

The review covered the system architecture, including the USSD token, USSDRebalancer, collateral configuration and minting flows, administrator-controlled settings, oracle implementations, Chainlink feeds, Uniswap V3 TWAP pricing, and the authorization boundaries governing protocol operations.

Our team identified a high-risk security posture in several price-sensitive components. Confirmed concerns include manipulable spot-price-based rebalancing with zero minimum output protection, an unrestricted SimOracle price setter, an incorrect WBTC price feed, insufficient oracle freshness and answer validation, and reliance on a single relatively short-duration TWAP for certain collateral valuations. These issues can enable undercollateralized issuance, inaccurate accounting, protocol losses, or denial of service depending on deployment configuration and market conditions.

System Overview

The USSD contract is the primary stablecoin and collateral-management component. It maintains the enabled collateral set, accepts collateral through mintForToken, calculates issuance amounts using calculateMint and collateralFactor, and obtains asset valuations from configured IStableOracle implementations. Administrative functions such as addCollateral, removeCollateral, setRebalancer, and setUniswapRouter are protected by the STABLE_CONTROL_ROLE, while the configured rebalancer receives privileged minting and burning capabilities.

USSDRebalancer manages the protocol's pool-based supply-balancing strategy. Its configuration includes the Uniswap pool, threshold, flutter ratios, and base asset, with updates restricted by its own STABLE_CONTROL_ROLE. The public rebalance function reads pool state through getOwnValuation and compares it with supply proportions before invoking BuyUSSDSellCollateral or SellUSSDBuyCollateral. These operations interact with USSD minting, burning, collateral valuation, and UniV3SwapInput execution paths.

The Hound team identified that rebalancing relies on the configured Uniswap V3 pool's instantaneous slot0 price rather than a protected time-weighted or independently validated reference. The subsequent swaps route through the configured Uniswap router with amountOutMinimum set to zero, leaving execution exposed to adverse price movement. This combination creates a material risk that temporary pool manipulation can influence both the rebalance decision and the resulting trade execution.

Oracle implementations include Chainlink-based StableOracleWETH and StableOracleWBTC contracts, Uniswap V3-based StableOracleDAI and StableOracleWBGL contracts, and the configurable SimOracle used for testing or simulated pricing. Our analysis revealed that SimOracle.setPriceUSD is unrestricted, while the Chainlink integrations do not adequately validate freshness, round completeness, or positive answers before downstream minting and collateral accounting consume the values. The WBTC implementation also points to the WETH/USD feed, causing WBTC collateral to be valued using the wrong asset price.

The Uniswap V3 StaticOracle component supports observation-period quotes using arithmetic mean ticks and weighted pool data. Although this provides some protection against instantaneous manipulation, the DAI and WBGL pricing paths remain dependent on individual pools and a 600-second observation period without robust liquidity checks, deviation limits, or independent reference validation. These controls should be strengthened alongside access restrictions, oracle circuit breakers, protected execution bounds, and deployment-time validation of all collateral and feed configurations.

Public SimOracle setter permits arbitrary collateral price manipulation

This oracle price-manipulation vulnerability is caused by an unrestricted setter in SimOracle that allows any account to change the stored collateral price. The setPriceUSD() function does not enforce access control, bounds, timelocks, or validation, while downstream USSD logic consumes the returned value directly for mint calculations and collateral accounting.

An attacker can set an artificially high collateral price and then use the minting path to obtain more USSD than the deposited collateral is worth. The manipulated value may also affect collateral-factor calculations and related rebalancing decisions. Exploitability depends on whether a production deployment uses SimOracle for an active collateral asset; if so, the issue permits arbitrary oracle manipulation and can lead to protocol undercollateralization.

Affected Components: the SimOracle contract, specifically the getPriceUSD() function, and the USSD contract, specifically the calculateMint() and collateralFactor() functions

QA Review: Upon reviewing SimOracle.sol and the consuming logic in USSD.sol, I confirmed that SimOracle exposes an unrestricted setPriceUSD(uint256) function that directly overwrites the public price storage variable. The function has no access control, role check, timelock, bounds validation, or caller restriction, so any account can change the value returned by getPriceUSD(). USSD.calculateMint() uses this value directly when determining the amount of USSD minted by mintForToken(), while collateralFactor() and the rebalancer’s BuyUSSDSellCollateral() and SellUSSDBuyCollateral() paths also consume the same oracle value. Although collateral configuration is restricted by USSD.onlyControl(), that protection does not restrict an already configured SimOracle or prevent an attacker from calling its setter. Consequently, if a deployed collateral entry uses SimOracle, an attacker can set an inflated price and obtain excessive USSD against deposited collateral or distort collateralization and rebalancing decisions. The finding is therefore confirmed at the code level, with production impact contingent on deployment configuration.
Suggested Mitigation (not independently verified): Do not use SimOracle in production; if it must exist, restrict updates to a controlled oracle role, add timelocks and bounds, and validate the configured oracle addresses during deployment.

Flash-loan manipulation of Uniswap spot price controls rebalancing trades

This price-manipulation vulnerability results from using the current Uniswap V3 spot price both to determine whether rebalancing is required and to size the resulting trades. The rebalancer obtains its valuation from the pool's slot0() state, which can be temporarily distorted through a large swap or flash-liquidity position. The resulting swaps are also executed with amountOutMinimum set to zero, providing no slippage or execution-price protection.

An attacker can manipulate the configured pool price, call the publicly accessible rebalance function while the price is distorted, and allow the rebalancer to trade against the manipulated state before unwinding the position. This may cause the protocol to buy or sell assets at materially unfavorable prices and incur significant losses. The absence of a trusted oracle, independent TWAP, deviation bound, or minimum-output constraint substantially increases the exploitability of the issue.

Affected Components: the USSDRebalancer contract, specifically the rebalance() and getOwnValuation() functions, and the USSD contract, specifically the UniV3SwapInput() function

QA Review: Upon reviewing USSDRebalancer.sol functions getOwnValuation and rebalance, and USSD.sol function UniV3SwapInput, I confirmed that the alleged spot-price manipulation vulnerability is exploitable. getOwnValuation reads uniPool.slot0().sqrtPriceX96 directly, with no TWAP, oracle comparison, observation-period requirement, or deviation bound. rebalance() is publicly callable and uses this instantaneous value both to select the recovery direction and to calculate the amount minted or traded. An attacker can temporarily move the configured USSD/DAI Uniswap V3 pool price through a large swap, invoke rebalance while the price is distorted, and then reverse the manipulation after the rebalancer executes. The resulting trades are routed through USSD.UniV3SwapInput, where IV3SwapRouter.ExactInputParams sets amountOutMinimum to zero and leaves the deadline commented out, so neither execution price nor transaction freshness is enforced. Although some trade sizing margins exist, they only address anticipated fees and do not protect against adversarial price movement. Therefore, the code demonstrates a clear exploitable manipulation path.
Suggested Mitigation (not independently verified): Use a sufficiently long-horizon TWAP or independent oracle for the trigger and sizing, enforce bounded price deviation, and pass nonzero amountOutMinimum values derived from a protected reference price with a deadline.

WBTC oracle uses the WETH/USD Chainlink feed

This oracle-mispricing vulnerability is caused by the WBTC oracle being configured with the WETH/USD Chainlink feed rather than the correct BTC/USD feed. Consequently, StableOracleWBTC.getPriceUSD() can return an ETH-denominated valuation for WBTC, producing incorrect collateral prices whenever ETH and BTC prices differ.

An attacker may deposit WBTC or trigger rebalancing while the erroneous valuation materially exceeds the asset's true market value. This can allow excessive USSD issuance or cause trades to execute using an incorrect collateral valuation, potentially leaving the protocol undercollateralized. The feed address should be verified against the intended deployment configuration and the underlying asset.

Affected Components: the StableOracleWBTC contract, specifically the getPriceUSD() function, and the USSD contract, specifically the calculateMint() and collateralFactor() functions

QA Review: Upon reviewing StableOracleWBTC.sol, I confirmed the oracle mispricing vulnerability. The StableOracleWBTC constructor hardcodes address 0x5f4eC3Df9cbd43714FE2740f5E3616155c5b8419, which is the Chainlink ETH/USD feed, while the contract comment identifies 0xf4030086522a5beea4988f8ca5b36dbc97bee88c as the intended BTC/USD feed. getPriceUSD() reads latestRoundData() from the incorrect feed and scales its eight-decimal result by 1e10 without any asset-identity, configuration, or deployment validation. If this oracle is registered for WBTC with minting enabled, USSD.calculateMint() uses the ETH price to determine the amount minted for deposited WBTC, allowing users to receive materially incorrect USSD amounts whenever BTC and ETH prices diverge. The same incorrect valuation is used by collateralFactor() and USSDRebalancer valuation and allocation logic, potentially causing further accounting and trading errors. No code-level guard checks the feed address, reported asset, price bounds, freshness, or consistency with WBTC. The issue is therefore directly exploitable, subject only to WBTC being configured as an active collateral.
Suggested Mitigation (not independently verified): Configure the verified BTC/USD feed for WBTC, make feed addresses immutable and deployment-validated, and add tests asserting that each collateral oracle references the expected asset feed.

Stale WETH/USD Chainlink answers can overvalue collateral during feed outages

This oracle price-mispricing vulnerability is caused by accepting Chainlink WETH/USD data without validating freshness, round completeness, or whether the returned price is positive. StableOracleWETH uses latestRoundData() and passes the result to USSD minting and collateral-accounting logic without an effective protocol-level staleness or deviation check.

During a feed outage or delayed update, an attacker can identify a stale price that remains higher than the current WETH market value and deposit WETH through mintForToken(). The attacker may receive excessive USSD and subsequently redeem or sell it before the oracle updates, leaving the protocol undercollateralized. Minting should be rejected when the answer is stale, incomplete, invalid, or outside configured bounds.

Affected Components: the StableOracleWETH contract, specifically the getPriceUSD() function, and the USSD contract, specifically the calculateMint(), mintForToken(), and collateralFactor() functions

QA Review: Upon reviewing StableOracleWETH.getPriceUSD and the consuming paths in USSD, I confirmed the reported oracle freshness vulnerability. StableOracleWETH calls priceFeed.latestRoundData() but discards roundID, startedAt, updatedAt, and answeredInRound, then directly converts the returned price and scales it by 1e10. It performs no validation that the answer is positive, the round is complete, or the timestamp is recent. USSD.calculateMint obtains this value without any additional validation and mintForToken transfers WETH into the contract before minting the calculated USSD amount, allowing a stale price above the market value to produce excess tokens. The same unchecked oracle value is used by collateralFactor when assessing total collateral. No protocol-level staleness, deviation, circuit-breaker, or pause check is present in the reviewed code. Consequently, if the Chainlink feed stops updating while retaining an inflated WETH/USD answer, an attacker can submit WETH through mintForToken and receive over-issued USSD before the feed recovers. The exploit depends on an external feed outage or delay, but the code provides no protection against that condition.
Suggested Mitigation (not independently verified): Require a valid positive answer, completed round, and updatedAt within a configured maximum age in StableOracleWETH. Add protocol-level stale-price checks and pause or reject minting when the feed is stale; consider a bounded secondary oracle or deviation circuit breaker.

Negative Chainlink answer is cast into an enormous positive collateral price

This oracle price-validation vulnerability results from converting a signed Chainlink price answer to uint256 without first verifying that the answer is positive and otherwise valid. A negative or invalid WBTC/USD response can therefore be interpreted as a very large unsigned collateral price and propagated into minting and collateral-accounting calculations.

If the feed returns a negative value because of an oracle failure, misconfiguration, or compromised data source, an attacker may invoke the WBTC collateral minting path while the invalid valuation is accepted. This could enable excessive USSD issuance and materially impair protocol solvency. The oracle must validate the sign, round status, freshness, and reasonable bounds of the answer before performing any unsigned conversion.

Affected Components: the StableOracleWBTC contract, specifically the getPriceUSD() function, and the USSD contract, specifically the calculateMint(), mintForToken(), and collateralFactor() functions

QA Review: Upon reviewing StableOracleWBTC.getPriceUSD, USSD.calculateMint, USSD.mintForToken, and USSD.collateralFactor, I confirmed that the signed Chainlink answer is cast directly from int256 to uint256 without checking that it is positive, complete, or fresh. In Solidity 0.8.x, this explicit conversion can reinterpret a negative value as a very large unsigned integer; it does not provide the required semantic validation. calculateMint then uses that value in collateral valuation and is publicly reachable through mintForToken, which has no caller restriction beyond token support and transfers the user-supplied collateral before minting. Although multiplication overflow may cause a revert for larger token amounts, sufficiently small amounts can avoid overflow through the subsequent divisions while still producing an enormously inflated stablecoin amount. collateralFactor is likewise exposed to invalid valuation and potential arithmetic failure. Therefore, if the configured feed returns a negative answer due to corruption, misconfiguration, or compromise, the code lacks guards to prevent the resulting unsafe valuation and minting behavior.
Suggested Mitigation (not independently verified): Require the Chainlink answer to be strictly greater than zero before casting, validate round completeness and freshness, and reject values outside reasonable protocol bounds before using them in collateral valuation.

Stale WBTC Chainlink answer accepted without freshness validation

This oracle price-validation vulnerability is caused by accepting WBTC/USD Chainlink responses without checking their timestamp, round completeness, or maximum age. StableOracleWBTC.getPriceUSD() returns the feed answer while ignoring updatedAt and answeredInRound, and the downstream minting path does not provide an independent freshness safeguard.

After the feed becomes stale, an attacker may deposit WBTC while the stored price remains materially above the asset's current market value. The public mintForToken() function could then issue more USSD than the collateral supports, allowing the attacker to redeem or sell the excess value and leave the protocol undercollateralized. The oracle should require a positive answer, a complete round, a nonzero update timestamp, and an update time within a configured maximum age.

Affected Components: the StableOracleWBTC contract, specifically the getPriceUSD() function, and the USSD contract, specifically the calculateMint() and mintForToken() functions

QA Review: Upon reviewing StableOracleWBTC.getPriceUSD in ussd-contracts/contracts/oracles/StableOracleWBTC.sol and the minting logic in USSD.sol, I confirmed the alleged oracle price validation vulnerability. getPriceUSD calls priceFeed.latestRoundData() but discards roundID, updatedAt, and answeredInRound, then directly converts the returned int256 price to uint256 and scales it by 1e10. No maximum-age, nonzero timestamp, round-completeness, positive-price, or other validity check is present. The value is consumed by USSD.calculateMint, which obtains the configured collateral oracle price and computes the amount of USSD to mint, and by the public mintForToken function after transferring collateral into the contract. Although mintForToken verifies that the token is an enabled mint collateral, this does not validate oracle freshness or accuracy. Consequently, if the Chainlink answer remains unchanged while WBTC market value falls, an attacker can deposit WBTC and receive excess USSD based on the stale valuation. The same stale value also affects collateralFactor accounting. No shown guard prevents this path.
Suggested Mitigation (not independently verified): Require price > 0, updatedAt != 0, answeredInRound >= roundId, and updatedAt within a configured maximum age before accepting the answer; revert or disable minting when the feed is stale, incomplete, or invalid.

Single-pool 10-minute TWAP remains manipulable for collateral valuation

This TWAP price-manipulation vulnerability results from relying on a single caller-selected Uniswap V3 pool and a fixed 10-minute observation period without liquidity checks, deviation limits, or independent price validation. The static oracle derives its quote from the consulted pool's historical tick, so the returned valuation remains dependent on the economic security and liquidity of that one market.

An attacker with sufficient capital or access to liquidity may move the pool price and maintain the distortion throughout the 600-second observation period. The manipulated TWAP could then be used to mint USSD or influence collateral-factor and rebalancing calculations. The practical cost depends on the configured pool's liquidity, but thin or concentrated liquidity can make sustained manipulation feasible.

Affected Components: the StableOracleDAI and StableOracleWBGL contracts, specifically their getPriceUSD() functions, and the UniswapV3StaticOracle contract, specifically the _quote() function

QA Review: Upon reviewing StableOracleWBGL.getPriceUSD and StableOracleDAI.getPriceUSD, together with StaticOracle._quote in UniswapV3StaticOracle.sol, I confirmed the stated TWAP design weakness. StableOracleWBGL fixes a single WBGL/WETH pool and requests a 600-second observation through quoteSpecificPoolsWithTimePeriod; _quote then uses only OracleLibrary.consult’s arithmetic mean tick, with no liquidity threshold, deviation bound, independent-market comparison, or sanity check. An attacker who can move and sustain that pool’s price across the observation window can therefore influence WBGL’s USD collateral valuation and the downstream USSD.calculateMint and collateralFactor calculations. The DAI oracle partially reduces this risk by averaging the Uniswap-derived value with a Chainlink DAI/ETH price, but it still incorporates the manipulable pool value and has no explicit deviation rejection. Moreover, its ethOracle is initialized to the zero address, so DAI pricing appears to revert unless deployment-specific code changes this state. Uniswap’s observation-period requirement prevents instantaneous manipulation but does not prevent sustained manipulation; exploit cost and practical severity require deployment liquidity analysis.
Suggested Mitigation (not independently verified): Use longer and liquidity-aware TWAPs, aggregate independent markets, reject low-liquidity or excessive-deviation observations, and compare the result with a trusted external reference before using it for minting or rebalancing.
