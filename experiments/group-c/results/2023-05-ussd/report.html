Executive Summary

The Hound security team conducted this comprehensive audit of the USSD protocol, focusing on its collateral-backed minting, oracle-based valuation, Uniswap-assisted rebalancing, and administrative control mechanisms.

The review covered the system architecture, including contract boundaries, end-to-end user and administrator flows, rebalancer operations, collateral configuration, oracle integrations, external token and protocol interactions, storage dependencies, and authorization boundaries.

Our team identified multiple high- and critical-severity risks, including unauthorized rebalancer minting and burning, unrestricted simulation-oracle price updates, manipulation of permissionless spot-price rebalancing, unsafe oracle validation, and incorrect collateral-feed configuration. Additional logic, arithmetic, and deployment-configuration issues may cause rebalancing failures or materially incorrect collateral valuation. The overall security posture is high risk until privileged operations, oracle assumptions, swap execution, and configuration validation are strengthened.

System Overview

The USSD contract is the primary upgradeable stablecoin component and implements the IUSSD interface. It maintains the configured collateral set, associated oracle references, collateral factors, the authorized rebalancer, and the Uniswap router address. Administrators holding STABLE_CONTROL_ROLE can initialize the system, add or remove collateral, configure the rebalancer, and set the swap router. Users invoke mintForToken, which calculates issuance using collateral balances and oracle-provided USD prices before transferring collateral and minting USSD.

Collateral valuation flows through IStableOracle implementations. StableOracleWETH and StableOracleWBTC obtain values from Chainlink-style feeds, while StableOracleDAI and StableOracleWBGL use StaticOracle and Uniswap V3 TWAP-style quotations. SimOracle provides a mutable price source intended for simulation. The architecture relies on these oracle outputs in calculateMint, collateralFactor, and rebalancer valuation, making feed correctness, freshness, sign handling, deployment-specific addresses, and access control central to the protocol's solvency.

USSDRebalancer implements IUSSDRebalancer and stores the configured Uniswap pool, USSD address, threshold, flutter ratios, and base asset. Its public rebalance function compares pool-derived valuation and supply proportions, then selects BuyUSSDSellCollateral or SellUSSDBuyCollateral. These operations call USSD minting or burning functions and route swaps through USSD.UniV3SwapInput, which in turn uses the configured Uniswap router. The rebalancer control role can change pool and strategy parameters, while USSD's configured rebalancer is intended to restrict swap execution.

The Hound team identified security-sensitive weaknesses across these flows. Rebalancing uses current pool spot state and balances, permits public triggering, and executes swaps without meaningful minimum-output protection. The rebalancer-only mint and burn functions are not consistently protected, and the collateral exclusion check can permit unintended pool-leg swaps. Arithmetic underflow conditions can also make recovery branches revert. Oracle implementations lack robust freshness and signed-value validation; one WBTC implementation uses an ETH/USD feed, the DAI oracle has an unusable ETH dependency, and the simulation oracle permits arbitrary public price changes.

StaticOracle provides pool preparation and weighted TWAP quotation functionality, but its specified-pool interface accepts pool addresses without demonstrating factory or token-pair validation, and its time-period preparation requires strict bounds and cardinality handling. Overall, the system's security depends heavily on administrator configuration and trusted external pricing, while several public or insufficiently constrained paths can affect supply, collateral accounting, trade execution, or protocol availability.

Unrestricted SimOracle price setter allows arbitrary oracle-price manipulation

This access control vulnerability allows any caller to set the price stored by SimOracle. The setPriceUSD() function directly writes the caller-supplied value to oracle storage without role-based authorization, governance approval, or other caller validation. The value is then exposed through getPriceUSD() to protocol integrations.

An attacker can set an arbitrary price, invoke minting, collateral-factor, or rebalancing operations that consume the manipulated value, and then restore or change the price. This enables direct manipulation of collateral valuations, mint amounts, and buy or sell decisions, creating a critical risk of unauthorized issuance, reserve depletion, or extraction of protocol value. The issue is particularly severe if SimOracle is used in a production deployment.

Affected Components: the SimOracle contract, specifically the setPriceUSD() and getPriceUSD() functions, and the USSD contract's mintForToken(), calculateMint(), and collateralFactor() functions together with the USSDRebalancer contract's buyUSSD() and sellUSSD() functions

QA Review: Upon reviewing the alleged access-control vulnerability in `SimOracle.setPriceUSD` at `ussd-contracts/contracts/oracles/SimOracle.sol`, I confirmed that the vulnerability clearly exists. The function assigns the caller-supplied `_price` directly to the public `price` storage variable and has no modifier, role check, owner check, or other authorization mechanism. Consequently, any address can replace the oracle value with zero, an inflated value, or any arbitrary number. `getPriceUSD` returns this mutable value without validation. The impact is exploitable where this oracle is configured in USSD collateral: `USSD.mintForToken` is publicly callable and uses `calculateMint`, which directly consumes the oracle price to determine minted supply; `collateralFactor` also uses it for accounting, while `USSDRebalancer` reads it during collateral valuation and rebalancing. Although USSD management functions use `STABLE_CONTROL_ROLE`, those protections do not restrict the separate oracle setter. The implementation comment identifies this as a simulation/test oracle, but no code prevents deployment or use in production. The hypothesis is therefore valid, subject to confirming deployment configuration.
Suggested Mitigation (not independently verified): Restrict setPriceUSD to a narrowly authorized governance or test-only role, or remove this oracle from production deployments. Enforce nonzero and protocol-specific bounds, and use a time-delayed, auditable update mechanism where mutable simulation pricing is required.

Permissionless rebalancing is manipulable through the Uniswap V3 spot price and pool balances

This economic manipulation vulnerability arises because the rebalancer relies on manipulable Uniswap V3 spot state and permits unrestricted execution without sufficient price protections. The valuation and supply-proportion calculations use the pool's current price and token balances, while the rebalance operation can be called publicly. The associated swaps also set the minimum output to zero, allowing execution at any price returned by the pool.

An attacker can use a flash loan or large temporary swaps or transfers to distort the pool price or balances, invoke rebalance() while the manipulated state is active, and then unwind the manipulation. This can cause the rebalancer to trade at materially unfavorable prices, transfer value to the attacker through arbitrage, or reduce protocol reserves. The risk is amplified by the absence of a TWAP, slippage limits, execution deadlines, or authorized keeper controls.

Affected Components: the USSDRebalancer contract, specifically the rebalance(), getOwnValuation(), and getSupplyProportion() functions, and the USSD contract's UniV3SwapInput() function

QA Review: Upon reviewing USSDRebalancer.rebalance, getOwnValuation, getSupplyProportion, and USSD.UniV3SwapInput, I confirmed that the alleged economic-manipulation vulnerability is exploitable. rebalance() is public and derives its decision from uniPool.slot0() through getOwnValuation(), making the trigger dependent on the current Uniswap V3 spot price rather than a TWAP or independent oracle. It also reads token balances directly from the pool in getSupplyProportion(), which reflect temporary swap state and can be affected during an atomic transaction. Once the manipulated state crosses the threshold, rebalance() executes asset conversions using UniV3SwapInput(), whose router parameters set amountOutMinimum to zero and leave the deadline commented out. Consequently, an attacker can temporarily move the pool price with a large swap or flash-loan-funded transaction, invoke rebalance, and allow the rebalancer to trade at an adverse price before unwinding the manipulation. No caller restriction, slippage validation, price-observation delay, or post-trade invariant prevents this path. Arithmetic checks may cause some manipulated calls to revert, but they do not mitigate unfavorable executable trades.
Suggested Mitigation (not independently verified): Use a sufficiently long TWAP or independently validated oracle for the trigger and sizing, validate pool liquidity/state, impose nonzero minimum outputs and deadlines, and restrict execution to an authorized keeper or enforce a commit/validation mechanism.

Peg-down rebalance can revert from unsigned subtraction underflow

This denial-of-service vulnerability is caused by unchecked unsigned subtraction in the rebalancer's trade-sizing and threshold calculations. In the peg-down branch, the code subtracts one pool balance from another without first confirming that the minuend is greater than or equal to the subtrahend. The configured threshold is also stored without an upper-bound check, allowing values greater than 1e6 to produce an invalid subtraction during threshold evaluation.

An attacker or unfavorable pool state can cause the DAI balance to exceed the USSD balance while the valuation remains below the peg, triggering a uint256 underflow and reverting rebalance(). Similarly, an improperly configured threshold can make the function revert whenever it is evaluated. Because rebalancing depends on this function, the issue can prevent corrective operations and create a denial of service until the pool state or configuration changes.

Affected Components: the USSDRebalancer contract, specifically the rebalance() and setTreshold() functions, and the rebalancer configuration storage

QA Review: Upon reviewing the rebalance() and setTreshold() implementations in USSDRebalancer.sol, I confirmed that the alleged denial-of-service vulnerability exists. In the peg-down branch, rebalance() evaluates (USSDamount - DAIamount / 1e12) / 2 without checking that the normalized USSD balance is at least the DAI balance. Because Solidity 0.8.6 reverts on underflow, any below-peg state with DAIamount / 1e12 greater than USSDamount causes rebalance() to fail before BuyUSSDSellCollateral() executes. The balance relation is not enforced by getSupplyProportion(), and an attacker can influence pool balances through permissionless token transfers or swaps, while rebalance() itself is publicly callable. Additionally, the condition ownval < 1e6 - threshold reverts when threshold exceeds 1e6, and setTreshold() imposes no upper bound. That configuration path is role-restricted, so it requires a privileged or compromised control account, but it remains an unmitigated permanent failure mode. No guards or clamping logic prevent either underflow.
Suggested Mitigation (not independently verified): Clamp trade sizes when the balance difference is negative, branch explicitly on the balance relation, and require threshold <= 1e6 in setTreshold before storing it.

Unrestricted mintRebalancer and burnRebalancer permit unauthorized supply manipulation

This access control vulnerability allows any external caller to invoke the sensitive mintRebalancer() and burnRebalancer() functions. Although the USSD contract defines an onlyBalancer authorization mechanism, these functions do not enforce it or otherwise verify that the caller is the configured rebalancer.

An attacker can mint tokens directly, alter total supply and contract-held balances, or burn balances repeatedly to disrupt the assumptions used by rebalancing and collateral accounting. These unauthorized supply changes can distort the protocol's valuation and supply ratios, interfere with legitimate rebalance operations, and potentially extract value from the system.

Affected Components: the USSD contract, specifically the mintRebalancer() and burnRebalancer() functions, the configured rebalancer storage, and the USSDRebalancer contract's rebalance() function

QA Review: Upon reviewing the rebalancer functions in ussd-contracts/contracts/USSD.sol, I confirmed an access-control vulnerability. The externally callable mintRebalancer(uint256) and burnRebalancer(uint256) functions invoke _mint(address(this), amount) and _burn(address(this), amount) without applying the contract’s existing onlyBalancer modifier or any equivalent authorization check. Consequently, any address can arbitrarily increase totalSupply by minting tokens to the USSD contract, and can burn any tokens currently held by the contract, subject only to the balance requirement enforced internally by _burn. The onlyBalancer modifier, defined immediately afterward, restricts msg.sender to address(rebalancer), but it is used only on UniV3SwapInput and does not protect either supply-management function. The configured rebalancer calls these functions during rebalance(), demonstrating that they are intended for privileged internal operation. Unauthorized minting can materially distort totalSupply and collateralFactor accounting and affect subsequent rebalancing decisions, while unauthorized burning can destroy contract-held supply. No other guard in the shown implementation prevents direct invocation.
Suggested Mitigation (not independently verified): Apply onlyBalancer to both functions, or use an explicit role restricted to the configured rebalancer; reject zero or invalid rebalancer addresses during configuration.

Oracle implementations accept invalid or unavailable prices

This oracle validation vulnerability allows invalid, stale, or unavailable feed data to be consumed as collateral prices. The oracle implementations cast signed Chainlink answers directly to uint256 without requiring a positive value, discard round and timestamp metadata, and do not enforce a maximum data age. In addition, the DAI oracle's ETH oracle dependency is assigned to the zero address and cannot be configured through a constructor or setter.

A stale, negative, incomplete, or otherwise invalid feed response can therefore affect minting, collateral valuation, and rebalancing. Configuring DAI collateral with the affected implementation may also cause price retrieval to fail or produce unusable results. These conditions can lead to incorrect collateralization, under- or over-minting, failed rebalancing, or loss of protocol funds.

Affected Components: the StableOracleWETH, StableOracleWBTC, and StableOracleDAI contracts, specifically their getPriceUSD() functions, as well as the USSD contract's calculateMint() function and the USSDRebalancer contract's rebalance() function

QA Review: Upon reviewing the oracle contracts and their consumers, I confirmed a real oracle-validation vulnerability. StableOracleWETH.getPriceUSD and StableOracleWBTC.getPriceUSD call latestRoundData() but discard roundId, updatedAt, and answeredInRound, perform no positive-price or staleness checks, and directly cast int256 price to uint256. A negative feed value therefore becomes an extremely large unsigned price, while an old but otherwise valid round remains usable. These values flow into USSD.calculateMint(), which is called by mintForToken(), and into collateralFactor() and USSDRebalancer.rebalance(), with no additional validation or freshness guard. Consequently, a stale or invalid feed can distort minting, collateral accounting, and rebalancing. StableOracleDAI additionally initializes ethOracle to the zero address and provides no setter or constructor injection; any getPriceUSD() call reaches ethOracle.getPriceUSD() and reverts, making DAI collateral configuration unusable and potentially causing denial of service in accounting or rebalancing paths. Although exploitation depends on feed state or collateral configuration, the source clearly lacks the stated safeguards.
Suggested Mitigation (not independently verified): Require price > 0, validate updatedAt and answeredInRound against the current round, enforce a maximum staleness bound, and inject and validate a nonzero ETH oracle before enabling the collateral.

StableOracleWBTC uses the ETH/USD Chainlink feed instead of BTC/USD

This configuration error causes the StableOracleWBTC contract to use an ETH/USD Chainlink feed as the price source for WBTC. The hardcoded feed address conflicts with the expected BTC/USD feed, so the value returned by getPriceUSD() does not represent the collateral asset being priced.

When WBTC is supplied as collateral, minting and collateral accounting consume the ETH price as though it were the WBTC price. Differences between ETH and BTC market prices can therefore produce materially incorrect collateral valuations, allowing users to mint more or less USSD than intended and potentially extract value from the protocol.

Affected Components: the StableOracleWBTC contract, specifically its constructor and getPriceUSD() function, and the USSD contract's mintForToken() and calculateMint() functions

QA Review: Upon reviewing StableOracleWBTC.sol, I confirmed the configuration error is present and can affect collateral valuation. The constructor assigns priceFeed to 0x5f4eC3Df9cbd43714FE2740f5E3616155c5b8419, the Ethereum mainnet Chainlink ETH/USD feed, while the source comment identifies 0xf4030086522a5beea4988f8ca5b36dbc97bee88c as the intended BTC/USD feed. getPriceUSD() calls latestRoundData() on the configured feed and scales its eight-decimal result by 1e10, thereby exposing the ETH/USD price as the WBTC/USD price. In USSD.sol, calculateMint() uses this oracle value directly to determine minted USSD for deposited collateral, and collateralFactor() uses it for total collateral accounting. Although addCollateral() is restricted to STABLE_CONTROL_ROLE, there is no validation that the oracle reports BTC/USD, and authorization only controls configuration; it does not correct the hardcoded feed. Consequently, whenever this oracle is registered for WBTC, users can mint or benefit from accounting based on the divergence between ETH and BTC prices. The issue is therefore exploitable under the stated deployment/configuration conditions.
Suggested Mitigation (not independently verified): Use the verified BTC/USD feed address for the target deployment, inject the feed address through a controlled constructor parameter, and validate that the configured feed's description, decimals, and network match BTC/USD before enabling the collateral.

medium

Collateral exclusion check is always true and can swap pool base assets incorrectly

This logic error causes the collateral exclusion check to evaluate as true for every token when determining whether a collateral asset should be swapped. The condition uses token != token0 || token != token1, although excluding an asset that matches either pool leg requires both inequalities to be true. For distinct token0 and token1 addresses, at least one inequality is always true, including when the collateral token equals token0 or token1.

When the over-peg rebalancing path processes a pool-leg asset, the rebalancer may execute an unintended pathbuy operation involving an asset that should have been excluded. This can result in an invalid or self-referential swap, cause rebalancing to revert, or spend newly acquired base assets through an unintended route, potentially causing reserve loss or denial of service.

Affected Components: the USSDRebalancer contract, specifically the SellUSSDBuyCollateral() function, and the USSD contract's UniV3SwapInput() function

QA Review: Upon reviewing USSDRebalancer.sol, I confirmed the reported logic error in SellUSSDBuyCollateral. For each underweight collateral, the exclusion check uses `collateral[i].token != uniPool.token0() || collateral[i].token != uniPool.token1()`. Because a Uniswap V3 pool has distinct token addresses, this expression is always true: a token matching token0 differs from token1, and a token matching token1 differs from token0. Consequently, the function invokes `IUSSD(USSD).UniV3SwapInput(collateral[i].pathbuy, daibought/portions)` even when the collateral token is a pool leg that the comment explicitly says must not be touched. A misconfigured collateral entry for USSD, the base asset, or another pool-leg address can therefore cause the rebalancer to execute an unintended route during the public rebalance() over-peg branch. UniV3SwapInput only restricts callers to the configured rebalancer and performs no path or token validation, so it does not mitigate the issue. Adding collateral requires STABLE_CONTROL_ROLE, meaning exploitation depends on privileged misconfiguration, but the faulty guard is real and operationally exploitable thereafter.
Suggested Mitigation (not independently verified): Replace the condition with token != uniPool.token0() && token != uniPool.token1(), validate every configured path against its input/output tokens, and skip or explicitly handle pool-leg collateral.

Network-specific hardcoded Chainlink feed can invalidate WETH pricing on non-mainnet deployments

This configuration error hardcodes a network-specific Chainlink feed address in StableOracleWETH without allowing the feed to be supplied, selected, or validated for the deployment network. The address may identify the intended WETH/USD feed on one network but may be absent, incompatible, or associated with a different asset on another network. Affected Components: the StableOracleWETH contract, specifically its constructor and getPriceUSD() function

QA Review: Upon reviewing the StableOracleWETH constructor and getPriceUSD function in StableOracleWETH.sol, I confirmed the configuration vulnerability.
