Executive Summary

The Hound security team conducted this comprehensive audit of the BlueBerry Protocol, focusing on its leveraged lending, vault, wrapper, spell, and oracle infrastructure.

The review covered the system architecture, including user and integration entry points through BlueBerryBank, SoftVault, HardVault, and strategy spells; interactions with Compound, Curve, Convex, Aura, ICHI, Uniswap, Balancer, and Paraswap; wrapped position custody; oracle routing and price-feed boundaries; protocol configuration; fee management; and asset and control flows across trusted and external components.

Our team identified several confirmed security and availability issues, including missing ERC20 approval-result handling, unsafe administrative oracle-route and Curve registry trust, stale mutable gauge resolution for existing positions, unchecked oracle metadata and deviation arithmetic, and zero-minimum-output swaps in CurveSpell, AuraSpell, and ShortLongSpell. The most significant risks affect oracle integrity, swap execution, collateral valuation, and operational availability. Overall, the protocol has meaningful defensive controls, such as access restrictions, freshness checks, per-source oracle failure isolation, balance-delta accounting, and explicit Compound error-code handling, but remediation of the confirmed findings and tighter governance of privileged dependencies are recommended before relying on the affected paths for production-scale assets.

System Overview

The Hound team analyzed BlueBerryBank as the central leveraged-position coordinator. Spells such as BasicSpell, CurveSpell, ConvexSpell, AuraSpell, IchiSpell, and ShortLongSpell route user operations into the bank, vaults, wrappers, external lending markets, liquidity protocols, and swap venues. BlueBerryBank depends on CoreOracle for collateral and debt valuation, while SoftVault integrates with Compound-style bToken markets and HardVault manages underlying-token deposits and ERC1155 share balances. FeeManager and ProtocolConfig provide shared fee and configuration parameters used by the bank, vaults, and strategy flows.

Our analysis revealed that the wrapper layer represents external positions through tokenized claims. WERC20 wraps underlying ERC20 balances, WCurveGauge deposits Curve LP tokens into gauges, WConvexPools and WAuraPools integrate with Convex and Aura pools, and WIchiFarm represents ICHI farm positions. These components custody LP or underlying assets and distribute rewards through position-specific accounting. A confirmed design risk exists in WCurveGauge because the token identifier preserves the gauge ID but not the resolved gauge address; if the external controller remaps that ID, later burns can target a different gauge from the one used at minting.

The oracle architecture consists of CoreOracle, AggregatorOracle, adapter contracts, and protocol-specific pricing modules. ChainlinkAdapterOracle and BandAdapterOracle consume external feed data with freshness controls, while CurveOracle, UniswapV2Oracle, UniswapV3AdapterOracle, BalancerPairOracle, and IchiVaultOracle derive prices from external pools, registries, or base-oracle values. AggregatorOracle isolates individual source failures and rejects unavailable or excessively divergent results, but confirmed weaknesses remain in privileged route selection, dynamically resolved Curve registries, feed and token decimal handling, and overflow-prone deviation arithmetic. These trust boundaries can affect collateral valuation, borrowing capacity, liquidations, and system availability.

We discovered that several spell-driven swaps lack effective execution-price protection. CurveSpell and AuraSpell pass zero minimum output and effectively unlimited deadlines to Uniswap routes, while ShortLongSpell forwards Paraswap data without independently enforcing meaningful output, route, or freshness constraints. Paraswap approval calls also ignore ERC20 return values, which can cause affected swaps to fail for non-compliant tokens. These integrations expose strategy assets and harvested rewards to adverse execution and transaction-ordering risks.

The system includes useful safeguards, including owner restrictions, bounded oracle freshness checks, per-source try/catch handling in AggregatorOracle, explicit Chainlink positivity checks, Compound error-code validation, balance-delta accounting in vaults and wrappers, and reentrancy protections in several position flows. Nevertheless, our analysis indicates that privileged configuration should be governed more tightly, external dependency identity should be validated or pinned, arithmetic and metadata assumptions should be bounded, and every reward or asset swap should enforce recipient, output, path, and deadline invariants at the protocol boundary.

Privileged route configuration can inject arbitrary asset prices

This oracle-integrity vulnerability stems from administratively controlled route selection without sufficient enforcement of route authenticity, token compatibility, or an approved-oracle allowlist. CoreOracle relies on the configured route and returned price without demonstrating that the selected implementation is authorized for the requested asset or that its output satisfies the system's expected integrity requirements.

An attacker who compromises or abuses the CoreOracle configuration authority could set a malicious route for a supported token and cause borrowing, repayment, collateral valuation, or liquidation operations to use an attacker-selected price. This is an arbitrary price-authority risk rather than ordinary market manipulation. Route changes should be tightly governed, delayed, monitored, and restricted to approved implementations and token-route pairs with validated decimals, freshness, contract code, and price bounds.

Affected Components: the CoreOracle contract, the ICoreOracle and IBaseOracle interfaces, and the configured oracle aggregation and route-dispatch logic

QA Review: Upon reviewing the CoreOracle setRoutes and _getPrice functions, I confirmed that privileged route configuration can directly control the price returned for any token. setRoutes is restricted only by onlyOwner and checks that token and route are nonzero; it does not verify that the route is an approved oracle, is associated with the configured token, or implements an authentic pricing mechanism. Subsequently, _getPrice obtains routes[token] and performs a raw IBaseOracle(route).getPrice(token) call, accepting any nonzero uint256 result. The only effective guards are route existence, CoreOracle pause state, and a nonzero price check, none of which constrain an intentionally malicious implementation from returning an arbitrary value. isTokenSupported repeats the same permissive call and therefore does not provide independent validation. AggregatorOracle limits source count and deviation only among owner-selected sources, so it does not mitigate a malicious route selected at the CoreOracle layer. Exploitation requires compromise or misuse of the owner authority, making this a privileged trust-boundary issue, but the code clearly permits arbitrary price injection through that authority.
Suggested Mitigation (not independently verified): Restrict route updates to a tightly governed authority and maintain an immutable or timelocked allowlist of approved oracle implementations and token-route pairs. Validate that each route is a contract, supports the configured token, returns a nonzero value within documented bounds, and preserves required decimals and freshness guarantees; emit events and provide delayed review for route changes.

CurveSpell reward swaps allow zero minimum output and are sandwichable

This slippage-manipulation vulnerability occurs because CurveSpell's reward-sale path permits a Uniswap V2 swap without enforcing a meaningful minimum acceptable output. When the minimum output is zero, the transaction provides no protection against execution at a price substantially worse than the quoted or expected value.

An attacker can monitor a pending harvest or close transaction, trade against the relevant reward-token pool to move its price, allow the unprotected swap to execute at the manipulated rate, and then reverse the trade. The resulting value loss is borne by the position or protocol. CurveSpell should require a validated, nonzero minimum output, a bounded execution deadline, and an appropriate quote derived from a trusted source or protected pricing mechanism.

Affected Components: the CurveSpell contract, its reward-harvesting and reward-token swap flow, the IUniswapV2Router interface, and the external Uniswap V2 router

QA Review: Upon reviewing the closePositionFarm function in CurveSpell, I confirmed that the reward-token swap lacks execution-price protection. After burning the wrapped gauge position, the function calculates rewards with _doCutRewardsFee(CRV), approves the caller-supplied swapRouter, and invokes swapExactTokensForTokens(rewards, 0, swapPath, address(this), type(uint256).max). The amountOutMin argument is explicitly zero, and the deadline is effectively unlimited. Consequently, a pending close transaction can be observed and preceded by trades that worsen the CRV-to-debt-token exchange rate; the router will still execute provided it returns any amount, with no oracle, TWAP, quoted minimum, or caller-signed slippage bound checked by CurveSpell. The swapRouter and swapPath are also supplied by the caller and are not validated in this function, increasing configuration and routing risk. Although downstream repayment may cause a manipulated transaction to revert if insufficient output is received, successful transactions can still execute at materially unfavorable prices, transferring value from the position to the sandwich attacker. The cited oracle contracts do not participate in this swap validation.
Suggested Mitigation (not independently verified): Require a nonzero minimum output computed from a trusted quote with a bounded slippage tolerance, or use a protected execution mechanism such as a deadline plus validated oracle/TWAP pricing; reject swaps whose output is below the bound and ensure the bound cannot be attacker-controlled without validation.

AuraSpell reward swaps may be executable with zero or caller-controlled slippage protection

This slippage-manipulation vulnerability results from insufficient validation of the minimum-output and deadline parameters used by AuraSpell when executing Uniswap swaps. Without an enforced, position-appropriate output bound and a short execution window, the swap may execute at a price determined by temporary pool manipulation.

An attacker can observe a pending AuraSpell transaction, trade against the relevant pool to move the exchange rate, allow the transaction to be sandwiched at the unfavorable price, and restore the market afterward. This can reduce the value received from harvested rewards or other swapped assets. AuraSpell should require a nonzero minimum output, validate the swap path and parameters, and enforce a caller-specified but bounded deadline before invoking Uniswap.

Affected Components: the AuraSpell contract and its integration with the external Uniswap router

QA Review: Upon reviewing the closePositionFarm function in AuraSpell, I confirmed the alleged slippage-manipulation vulnerability. For every harvested reward token, the contract calls swapRouter.swapExactTokensForTokens with the full reward balance, an amountOutMin of 0, the caller-supplied swapPath[i], address(this) as recipient, and type(uint256).max as the deadline. Consequently, any amount of output, including an economically worthless amount, satisfies the swap, and the transaction remains executable indefinitely rather than being constrained to a short user-selected validity window. No oracle comparison, minimum-output validation, path validation, router allowlist, or deadline check is performed before the external swap. Although subsequent repayment and LTV validation may cause the overall transaction to revert if insufficient assets are received, these checks do not provide price protection and cannot prevent a sandwich when the resulting output remains sufficient for execution. A pending closePositionFarm transaction using a legitimate router can therefore be front-run and back-run to manipulate pool pricing, causing the spell to accept materially worse reward conversions.
Suggested Mitigation (not independently verified): Require a nonzero, position-appropriate minimum output and a short user-specified deadline; validate swap paths and reject unsafe parameters before invoking Uniswap.

ShortLongSpell Paraswap execution permits insufficient-output swaps

This slippage-manipulation vulnerability arises because ShortLongSpell relies on Paraswap execution without independently enforcing a sufficient minimum output and route-freshness constraint at the spell boundary. Permissive calldata or an unchecked minimum-output value can allow a swap to complete even when the actual proceeds are substantially below the expected amount.

An attacker may submit or front-run a ShortLongSpell operation, manipulate the relevant execution venue before the transaction is mined, and cause collateral or another position asset to be sold at an unfavorable rate. This can result in direct value loss and inaccurate position accounting. ShortLongSpell should validate the source and destination assets, input amount, minimum output, and deadline, reject unbounded values, and verify the actual balance change before finalizing accounting.

Affected Components: the ShortLongSpell contract, the PSwapLib library, the IParaswap interface, and the external Paraswap protocol

QA Review: Upon reviewing ShortLongSpell.openPosition, _deposit, closePosition, and _withdraw, I confirmed that the boundary does not independently enforce a meaningful minimum output or freshness constraint. openPosition validates only that swapData.fromToken matches the borrow token and that the strategy token is correct; it does not constrain swapData.fromAmount, toAmount, expectedAmount, or deadline. _deposit relies on Paraswap's caller-controlled toAmount and separately checks the received balance against the equally caller-controlled expectedAmount, allowing both values to be zero or otherwise permissive. In the close path, _withdraw invokes PSwapLib.megaSwap without checking the returned amount or comparing received tokens against expectedAmount, while sellSlippage is only bounded against configuration and is not connected to swapData. PSwapLib merely approves data.fromAmount and forwards the entire structure to Augustus, providing no validation. Consequently, a transaction submitted with a permissive minimum can execute after adverse price movement and accept substantially less output; the source shows no independent protection against this route.
Suggested Mitigation (not independently verified): Require a caller-supplied minimum output that is checked against the actual Paraswap result, reject zero or otherwise unbounded minimums where appropriate, validate the source token, destination token, and input amount against the operation, and require a bounded deadline or equivalent freshness condition. Independently verify returned balances before finalizing position accounting.

Externally Mutable Curve Address Provider Can Replace the Trusted Registry

This oracle-integrity vulnerability results from allowing CurveOracle's address-provider and registry resolution path to determine the underlying pricing source without pinning or otherwise validating the resolved registry. The oracle therefore trusts an externally mutable dependency for LP-token mappings and virtual-price data.

If the relevant Curve governance or address-provider authority is compromised, or if an improperly configured deployment supplies a malicious provider, the registry returned to CurveOracle could map assets to attacker-selected pools or return manipulated pricing data. This permits replacement of the oracle data source itself, rather than merely influencing a market price. Deployments should pin a vetted registry where possible, restrict and timelock provider changes, validate resolved contracts against an allowlist, and monitor changes with emergency response controls.

Affected Components: the CurveOracle contract, the CurveAddressProvider and CurveRegistry interfaces, and the external Curve address-provider and registry contracts

QA Review: Upon reviewing the CurveOracle constructor and _getPoolInfo function, I confirmed that the oracle trusts dynamically resolved Curve registry addresses without validating their identity or implementation. Although addressProvider is immutable, its get_registry(), get_address(5), and get_address(7) results are queried on every price request, so an address-provider administrator or a misconfigured deployment can redirect resolution to an arbitrary contract. CurveOracle then immediately invokes get_pool_from_lp_token, get_n_coins, get_coins, and get_virtual_price_from_lp_token on that returned address. The only substantive guard is whether the reported pool is nonzero; there is no allowlist, code-hash check, expected-provider validation, or verification that the pool and LP token correspond. A malicious registry can therefore select attacker-controlled underlying tokens and virtual prices, and getPrice subsequently trusts those values when calculating LP prices. CoreOracle only checks that the configured route returns a nonzero value and does not mitigate this dependency. Exploitation requires control or compromise of the provider’s administration, or an incorrectly configured provider, but the code provides no protection once that condition exists.
Suggested Mitigation (not independently verified): Pin a vetted registry address at deployment where possible, or restrict and timelock any provider changes. Validate the resolved registry against an allowlist and verify expected code/interface behavior before accepting prices; add monitoring and emergency pause controls for registry changes.

medium

ERC20 approval return values are ignored

This input-validation vulnerability arises because PSwapLib invokes IERC20.approve() without checking its return value or verifying that the requested allowance was established. ERC20 token calls do not automatically revert when a token returns false, so the library may treat a failed approval as successful.

If a supported or configured token reports approval failure without reverting, PSwapLib continues by calling Paraswap. The subsequent swap may fail, or downstream accounting may proceed under the assumption that the required allowance exists, disrupting the intended operation. The library should use SafeERC20-compatible approval handling and explicitly support tokens that require an allowance to be reset to zero before being changed.

Affected Components: the PSwapLib library, specifically its _approve() function, and the external Paraswap protocol

QA Review: Upon reviewing PSwapLib._approve in blueberry-core/contracts/libraries/Paraswap/PSwapLib.sol, specifically the two approve calls at lines 14-15, I confirmed that ERC20 return values are ignored. The function first invokes inToken.approve(spender, 0) and then inToken.approve(spender, amount), but neither result is checked and no SafeERC20 wrapper is used. Consequently, a token that returns false without reverting, or otherwise fails to establish the requested allowance, will not cause _approve to fail. megaSwap then unconditionally invokes IParaswap(augustusSwapper).megaSwap(data) at line 25. In the common case, Paraswap's subsequent transferFrom will revert because allowance is missing, creating a denial-of-service condition for that token; token-specific behavior could also produce inconsistent or unsafe outcomes. The shown code contains no token allowlist, return-value validation, allowance postcondition check, or other guard that mitigates this behavior. The issue is therefore real, although practical impact depends on whether such non-compliant tokens can be supplied or configured.
Suggested Mitigation (not independently verified): Use OpenZeppelin SafeERC20.safeApprove or safeIncreaseAllowance-compatible logic, and explicitly handle tokens requiring zero-before-nonzero approval. Restrict supported assets if token behavior cannot be normalized.

Curve gauge remapping can strand or misroute existing wrapped positions

This logic error occurs because wrapped-position identity depends on a mutable gauge-controller mapping rather than on an immutable gauge address or a versioned mapping recorded at mint time. WCurveGauge.mint() deposits into the gauge resolved at that time, but WCurveGauge.burn() decodes the position identifier and resolves the gauge again using the current controller mapping.

If the controller later remaps the same gid to a different gauge, redemption may call withdraw() on the replacement gauge and attempt to transfer its associated LP token instead of interacting with the gauge in which the position was originally deposited. Existing positions may consequently become unredeemable or be routed to the wrong asset. The position should record the resolved gauge address or mapping version and reject or explicitly migrate positions when the mapping changes.

Affected Components: the WCurveGauge contract, specifically mint() and burn(), the ILiquidityGauge interface, and the external Curve gauge-controller and gauge contracts

QA Review: Upon reviewing WCurveGauge.sol, I confirmed the alleged position-remapping logic error. The mint function resolves gaugeController.gauges(gid) at mint time, transfers the gauge's lp_token into the wrapper, deposits the amount into that gauge, and encodes only gid and accCrvPerShares[gid] into the ERC1155 token ID. Conversely, burn decodes the same ID and independently queries gaugeController.gauges(gid) again before calling _mintCrv, withdraw, and lp_token transfer. There is no stored gauge address, mapping version, or equality check against the gauge used during minting. If the controller mapping for gid changes, an existing token can therefore attempt withdrawal from the replacement gauge. If the wrapper lacks sufficient balance there, redemption reverts and the position is stranded; if it has deposits in the replacement gauge, the burn may withdraw and transfer the replacement gauge's LP token, misrouting the position. Reentrancy protection and balance burning do not address this stale external mapping dependency.
Suggested Mitigation (not independently verified): Store the resolved gauge address or a mapping version in the position identity and redeem against that immutable value. Alternatively reject burns when the current controller mapping differs from the mapping recorded at mint and provide an explicit migration path.

Unbounded Chainlink feed decimals can distort or disable price conversion

This oracle-integrity vulnerability is caused by using feed-supplied decimal metadata for price scaling without enforcing a supported range or validating the resulting arithmetic. An improperly configured or nonstandard Chainlink feed may report an extreme decimals value, causing exponentiation or normalization to overflow, underflow, or produce an incorrectly scaled price.

Such a feed can make dependent price queries revert, disrupting oracle-dependent operations, or can cause downstream components to consume a materially distorted normalized value. The Chainlink adapter should validate feed decimals before scaling, use checked arithmetic with separate handling for values above and below the target precision, and reject results that overflow, underflow, or round to zero.

Affected Components: the ChainlinkAdapterOracle contract, the feed-registry interface, and the configured Chainlink price-feed contracts

QA Review: After analyzing ChainlinkAdapterOracle.getPrice, I confirmed that feed-provided decimals are used without an explicit supported-range or result-validity check. The function retrieves uint8 decimals through registry.decimals(token, USD), obtains the answer, and then evaluates (answer.toUint256() * Constants.PRICE_PRECISION) / 10 ** decimals. Because decimals can range up to 255, values of approximately 78 or greater cause 10 ** decimals to overflow under Solidity 0.8 checked arithmetic, reverting every price request for the affected token. More generally, unusual metadata can produce unsupported scaling behavior, while multiplication may independently overflow for sufficiently large answers. The positive-answer and freshness checks do not protect the exponentiation or multiplication, and CoreOracle merely propagates the revert through _getPrice (although isTokenSupported catches it). Exploitation requires a registry/feed configuration capable of returning malicious or erroneous decimals, generally through the owner-controlled registry or a compromised/misconfigured upstream component, so this is primarily an oracle availability and integrity risk rather than a permissionless attack.
Suggested Mitigation (not independently verified): Validate feed decimals against an explicit supported range before exponentiation and normalize using checked arithmetic with separate branches for decimals above and below 18. Reject unsupported feeds or scaling results that overflow, underflow, or round to zero.

BaseOracleExt deviation arithmetic can overflow and brick dependent price reads

This availability vulnerability arises from overflow-prone arithmetic in BaseOracleExt's maximum-relative-deviation calculation. The component processes externally sourced uint256 prices without first constraining their magnitude or using an overflow-safe method for multiplication and scaling.

If a configured price source returns an abnormally large value, such as through an extreme-decimal token configuration or a malicious or faulty feed, a dependent price query may revert while performing the deviation check. This can brick downstream oracle reads and disrupt borrowing, valuation, or liquidation operations. BaseOracleExt should bound input prices and deviation parameters, use division-first or full-precision mulDiv arithmetic, and reject values that cannot be represented safely.

Affected Components: the BaseOracleExt contract, the OracleAggregator contract, and the CoreOracle contract

QA Review: Upon reviewing the deviation validation in BaseOracleExt._isValidPrices and its callers in AggregatorOracle.getPrice, I confirmed an availability vulnerability. The function computes ((maxPrice - minPrice) * Constants.DENOMINATOR) / maxPrice without bounding either price or using overflow-safe multiplication. Although Solidity 0.8 reverts on overflow, that behavior causes the entire AggregatorOracle.getPrice call to fail when two configured sources return sufficiently large, closely valued prices; the deviation cap only constrains maxPriceDeviation and does not constrain source prices. The try/catch in AggregatorOracle.getPrice surrounds only each individual source getPrice call, not the subsequent deviation calculation, so it cannot contain this revert. Additionally, the averaging expressions prices[0] + prices[1] and prices[1] + prices[2] can independently overflow for near-maximum values even when the deviation calculation succeeds. CoreOracle._getPrice directly propagates aggregator reverts, causing dependent price reads to fail. Exploitation requires a configured source to return abnormal values, but the code provides no protective bound against that condition.
Suggested Mitigation (not independently verified): Validate that all input prices and the configured deviation are within safe bounds before arithmetic; calculate deviations using division-first or full-precision mulDiv logic, and reject values that cannot be represented safely.

This availability vulnerability results from the absence of constructor validation for the external base-oracle dependency. UsingBaseOracle stores the supplied address as an immutable interface reference without checking whether it is the zero address or points to deployed contract code.

A deployment or configuration authority that supplies an invalid address can therefore create a contract whose pricing calls permanently fail. IchiVaultOracle depends on the configured base oracle when calculating prices, so an invalid dependency can disable oracle-dependent operations without requiring an external attacker to compromise the contract after deployment. The constructor should reject zero or non-contract addresses and, where appropriate, validate that the oracle returns a valid price.

Affected Components: the UsingBaseOracle contract, specifically its constructor, and the IchiVaultOracle contract, specifically getPrice()

QA Review: Upon reviewing the UsingBaseOracle constructor and IchiVaultOracle.getPrice, I confirmed that the reported availability weakness exists. UsingBaseOracle.constructor directly stores the supplied IBaseOracle address in the immutable base variable without checking for address(0), deployed code, or functional oracle behavior. IchiVaultOracle.getPrice subsequently invokes base.getPrice(token0) and base.getPrice(token1) after obtaining vault data, so a zero address, EOA, or incompatible contract will generally cause the external call or ABI decoding to revert for vaults with nonzero supply. No validation is added by IchiVaultOracle.constructor, which merely forwards the argument to the base constructor, and no fallback pricing path exists in getPrice. The issue is primarily a deployment or trusted-configuration error rather than an arbitrary external attacker compromising an existing deployment; however, an actor able to deploy or register the oracle can permanently create a nonfunctional pricing instance. Constructor checks for nonzero address, deployed code, and preferably a valid price response would mitigate it.
Suggested Mitigation (not independently verified): Reject address(0) and require address(_base).code.length > 0 in the constructor. Validate that the supplied oracle returns a valid nonzero price for required base assets before registering the deployment.
