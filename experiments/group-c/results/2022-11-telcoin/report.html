Executive Summary

The Hound team conducted this comprehensive audit of the Telcoin Staking and FeeBuyback System, including its staking, reward distribution, plugin, administrative, migration, and fee-conversion functionality.

The review covered the system architecture and trust boundaries connecting staking users, the StakingModule, pluggable IPlugin reward contracts, TEL and other ERC-20 tokens, FeeBuyback, external wallets, swap aggregators, safe addresses, and privileged administrative roles.

Our team identified several high-severity issues affecting availability, asset accounting, reward accessibility, migration authorization, and privileged asset control. Key risks include denial of service through invalid plugins, reward stranding after plugin removal, arbitrary calls by the FeeBuyback owner, misallocation of residual TEL, missing swap-output validation, and unrestricted reward or principal redirection by RECOVERY_ROLE. The system’s security posture depends heavily on trusted administrative roles and correctly configured external components, and remediation should prioritize role containment, plugin lifecycle controls, balance-delta accounting, and strict external-call validation.

System Overview

The Hound team analyzed the StakingModule as the core user-facing contract. Users stake TEL through stake, receive checkpointed stake balances, and can exit, claim rewards, or combine claiming and exiting. The module maintains total staked principal and user checkpoints, transfers TEL through ERC-20 operations, and invokes registered IPlugin contracts to calculate claimable rewards, process claims, and receive stake-change notifications.

The StakingModule uses a plugin registry composed of the plugins array, nPlugins, and pluginsMapping. SimplePlugin implements IPlugin and maintains per-user claimable checkpoints together with aggregate amounts owed. It is funded through increaseClaimableBy, is restricted so that the StakingModule performs user claims, and transfers TEL directly to claim recipients. Our analysis revealed that plugin registration and callback execution form a significant trust boundary: arbitrary or reverting registered addresses can affect staking, exit, claim, and view operations, while removing a plugin can leave its outstanding liabilities inaccessible through normal user paths.

We reviewed the FeeBuyback flow connecting the fee-rewards safe, external swap aggregator, FeeBuyback, and SimplePlugin. FeeBuyback can obtain fee tokens from the safe, execute an owner-supplied external call, swap assets through the configured aggregator, and approve SimplePlugin to pull TEL for referral rewards. We discovered that the flow relies on unrestricted owner-controlled calls, does not verify swap output, does not consistently check ERC-20 return values, and credits the entire current TEL balance rather than the balance increase attributable to the current submission.

Administrative and recovery controls include SLASHER_ROLE, PLUGIN_EDITOR_ROLE, PAUSER_ROLE, RECOVERY_ROLE, TieredOwnership controls, and the initialization authority. These controls can modify plugins, pause operations, slash stakes, rescue tokens, and execute migration-only functions. The Hound team identified that RECOVERY_ROLE can invoke claimAndExitFor with independent source and destination addresses, allowing a compromised or misused recovery operator to redirect user principal and rewards. Initialization also requires atomic deployment-time execution to prevent an uninitialized proxy from being claimed by an attacker.

The architecture otherwise uses role guards, pausing, reentrancy protection, checkpointed accounting, and SafeERC20 operations in portions of the staking and plugin flows. However, these mechanisms do not compensate for missing validation at trust boundaries. Our analysis revealed that the most important improvements are to validate plugin code and interfaces, preserve or settle liabilities before plugin removal, constrain arbitrary external calls, measure token balance deltas, enforce minimum swap outputs, verify transfer results, and bind privileged migrations to explicit user authorization.

Unvalidated plugin registration enables global denial of service

This denial-of-service vulnerability results from insufficient validation of registered plugins and the treatment of plugin callbacks as mandatory trusted operations. The plugin registry does not verify that an address contains contract code or implements the expected interface. In addition, stake-change processing invokes every registered plugin even when the plugin indicates that notification is not required.

A holder of PLUGIN_EDITOR_ROLE, or an attacker who compromises that role, can register an invalid, reverting, or deliberately gas-intensive plugin. Subsequent staking, claiming, exit, or view operations that interact with the registry may revert or consume excessive gas, preventing normal users from using core staking functionality. The impact can be reduced by validating plugin code and interfaces, bounding the number of plugins, honoring the requiresNotification setting, and isolating callback failures from core operations.

Affected Components: the StakingModule contract, specifically addPlugin(), _notifyStakeChangeAllPlugins(), claim(), and claimable(), together with the plugin registry and staking entry points that trigger plugin notifications

QA Review: Upon reviewing the StakingModule plugin-management and callback paths, I confirmed that a PLUGIN_EDITOR_ROLE holder can register an arbitrary address without a nonzero-code check, interface validation, or plugin-count bound. The addPlugin function only checks pluginsMapping, after which the address is iterated by claimable, claimableAt, totalSupply, _claim, and _notifyStakeChangeAllPlugins. The requiresNotification guard is commented out, so every registered address receives notifyStakeChange during stake, exit, partial exit, and slash-related flows. A malicious contract can therefore deliberately revert in notifyStakeChange or any view/claim callback, causing affected operations to revert for all users. An EOA or incompatible contract can also cause ABI decoding failures in functions expected to return values such as claimable or totalClaimable. Although removePlugin allows an authorized operator to recover by removing the address, it does not prevent the denial of service while the plugin remains registered, and pausing does not make view calls succeed. SimplePlugin itself safely implements a no-op notification, but that does not constrain other registered addresses.
Suggested Mitigation (not independently verified): Require nonzero contract code and validate the expected interface before registration; enforce a bounded plugin count; invoke notifyStakeChange only when requiresNotification returns true; consider isolating callback failures so one plugin cannot halt core staking operations.

Removing a plugin can permanently strand user rewards

This asset-loss vulnerability is caused by removing a plugin without settling, preserving, or rerouting the user balances associated with that plugin. The active plugin registry is changed immediately, while the plugin's outstanding claimable balances remain recorded in the removed plugin.

Because SimplePlugin.claim() is restricted to calls from the staking module, users cannot directly withdraw balances from a removed plugin. A plugin editor can therefore remove a plugin with outstanding rewards, permanently preventing claims unless the plugin is later restored. The system should require migration or settlement before removal, retain claim access until all liabilities are cleared, or provide an explicit recovery mechanism for affected users.

Affected Components: the StakingModule contract, specifically removePlugin(), totalSupply(), and claimable(), and the SimplePlugin contract, specifically claim(), along with the plugin registry and per-plugin claimable-balance storage

QA Review: Upon reviewing StakingModule.removePlugin, claim, claimFromIndividualPlugin, claimable, and SimplePlugin.claim, I confirmed that plugin removal can strand outstanding rewards. removePlugin removes the plugin from the active plugins array and sets pluginsMapping to false without checking totalClaimable, settling user balances, or preserving a claim route. All user-facing claim paths iterate only over the current active plugins, and SimplePlugin.claim is protected by onlyStaking, requiring the StakingModule as msg.sender; therefore users cannot call the removed plugin directly. The plugin retains each user’s checkpoints and _totalOwed, and its TEL balance remains reserved, but those assets are inaccessible through normal user functionality after removal. The PLUGIN_EDITOR_ROLE can technically restore access by calling addPlugin with the same address, so permanent loss is not mathematically inevitable from this code alone; however, users have no independent recovery mechanism if administrators decline to re-add it or the plugin is operationally deprecated. claimAndExitFor does not mitigate this because it also iterates only active plugins and is restricted to RECOVERY_ROLE. Thus, the core reward-stranding vulnerability is real, although the hypothesis's claim of irreversible loss is conditional.
Suggested Mitigation (not independently verified): Require a migration or settlement procedure before removal, keep removed plugins claimable until all liabilities are zero, and maintain removed-plugin claim routing or an explicit recovery mechanism for affected users.

FeeBuyback credits all residual TEL balance to the current referral

This asset-loss vulnerability is caused by FeeBuyback deriving referral rewards from its entire current TEL balance rather than from the TEL generated by the current submission. Both the direct-TEL and aggregator paths pass the contract's full balance to SimplePlugin.increaseClaimableBy(), without recording a pre-operation balance or validating the incremental output.

When FeeBuyback holds residual TEL, an authorized submission can credit a selected recipient with that entire balance and transfer it into SimplePlugin. The same issue can occur when a swap produces less TEL than expected, because pre-existing funds are treated as the current operation's proceeds. The contract should credit only the positive balance delta measured around the transfer or swap, validate minimum output, and isolate unsolicited or residual balances.

Affected Components: the FeeBuyback contract, specifically submit(), and the SimplePlugin contract, specifically increaseClaimableBy(), including the referral claimable-balance storage

QA Review: Upon reviewing FeeBuyback.submit in contracts/fee-buyback/FeeBuyback.sol, I confirmed the alleged asset-loss vulnerability. In the direct-TEL branch, the contract transfers only amount from _safe, but then approves and credits _telcoin.balanceOf(address(this)) to recipient through _referral.increaseClaimableBy. Consequently, any TEL already held by FeeBuyback is included in the recipient's reward. The aggregator branch has the same defect: after the swap, it uses the contract's entire current TEL balance rather than measuring the balance increase attributable to that swap. SimplePlugin.increaseClaimableBy then records the supplied amount as claimable and pulls exactly that amount from FeeBuyback using transferFrom, so the residual balance is transferred into the plugin and assigned to the chosen recipient. There is no before/after balance accounting, output validation, or guard excluding pre-existing TEL. Although submit is restricted by onlyOwner, that is an authorization boundary rather than protection against a malicious, compromised, or improperly acting owner, and the owner can select an arbitrary recipient. The hypothesis is therefore directly supported by the implementation.
Suggested Mitigation (not independently verified): Record the TEL balance immediately before the transfer or swap, calculate the positive balance delta afterward, and credit only that delta. Validate the swap output and use SafeERC20 for all token transfers and approvals; isolate or reject unsolicited and residual balances.

RECOVERY_ROLE can redirect users’ migrated principal and rewards to an arbitrary recipient

This access-control vulnerability allows RECOVERY_ROLE to redirect a user's migrated principal and rewards to an arbitrary recipient. The migration-only function relies solely on role authorization and does not authenticate the affected user, constrain the destination, or require proof that the migration was authorized by that user.

A compromised or misused recovery account can call claimAndExitFor() with a victim as the source account and an attacker-controlled address as the recipient. The function then executes both the victim's claim and exit transfers, potentially transferring the victim's entire staking position and accrued rewards. The system should require a user-signed migration authorization with replay protection, restrict destinations to the user or an approved migration contract, and record migration nonces in events.

Affected Components: the StakingModule contract, specifically claimAndExitFor(), _claim(), and _exit(), the RECOVERY_ROLE authorization path, and stake storage

QA Review: Upon reviewing StakingModule.claimAndExitFor, _claim, and _exit, I confirmed that a holder of RECOVERY_ROLE can redirect both a user’s claimable rewards and staked TEL to an arbitrary address. claimAndExitFor accepts independent account and to parameters, invokes _claim(account, to, auxData), and then _exit(account, to); neither internal function authenticates the user, validates the destination, or requires migration authorization. _claim causes each plugin to send rewards directly to to, while _exit transfers the entire recorded stake to the same address after clearing the account’s checkpoint. The whenPaused modifier and nonReentrant guard do not prevent misuse once the contract is paused; importantly, RECOVERY_ROLE itself cannot pause the contract, so exploitation by that role alone requires an already-paused state or additional PAUSER_ROLE privilege. Nevertheless, the code provides no consent or cryptographic proof tying the migration to the affected account, making arbitrary redirection possible for a compromised or misused recovery operator. This is a privileged-role abuse issue rather than an unprivileged exploit.
Suggested Mitigation (not independently verified): Require a user-signed migration authorization binding account, destination, nonce, and migration parameters, or restrict to to == account or an approved migration contract. Add replay protection and emit events containing the authorized destination and migration nonce.

Owner-controlled arbitrary call enables FeeBuyback asset and approval exfiltration

This access-control vulnerability gives the FeeBuyback owner a generic arbitrary-call capability. The submit() function accepts a caller-selected target address and calldata, then executes the call from the FeeBuyback contract without restricting the destination, function selector, or operation to the documented wallet transaction.

If the FeeBuyback owner is compromised or an owner-controlled execution path is abused, an attacker can invoke token transfers, modify allowances, or perform other actions against assets held by FeeBuyback. The arbitrary call should be replaced with narrowly defined operations or constrained by an immutable or administratively governed target and selector allowlist, with explicit protection for token balances and allowances.

Affected Components: the FeeBuyback contract, specifically submit(), the FeeBuyback owner authorization path, and the configured wallet or service-wallet call target

QA Review: Upon reviewing FeeBuyback.submit in contracts/fee-buyback/FeeBuyback.sol, I confirmed that the contract grants an unrestricted arbitrary-call capability to any address recognized by onlyOwner(). The function accepts caller-controlled wallet and walletData parameters and executes wallet.call{value: 0}(walletData) without validating the target, function selector, or calldata contents. Consequently, an authorized owner can set wallet to an ERC20 token contract and provide transfer(address,uint256) calldata to move tokens held by FeeBuyback, or provide approve(address,uint256) calldata to grant an attacker-controlled spender an allowance. The call executes with FeeBuyback as msg.sender, so token contracts will treat the FeeBuyback balance and approvals as the affected assets. The subsequent token, recipient, and amount checks do not prevent this because the arbitrary call occurs first and execution can return early when those values are zero. Although onlyOwner restricts exploitation to the owner or a compromised owner key, it does not constrain the operation to the intended primary wallet transaction. No target or selector allowlist exists, so the reported access-control issue is real.
Suggested Mitigation (not independently verified): Replace the generic wallet.call with narrowly specified operations or enforce an immutable/administrative allowlist of wallet targets and permitted function selectors; validate calldata and prohibit calls that transfer FeeBuyback assets or modify arbitrary allowances.

Successful aggregator call is accepted without verifying TEL output

This asset-loss vulnerability occurs because FeeBuyback treats any successful low-level aggregator call as a valid swap without verifying that the required amount of TEL was received. The implementation transfers source tokens and checks only the call status, with no post-swap TEL balance increase or minimum-output requirement.

A malformed or manipulated swap payload, adverse execution, or compromised aggregator can therefore return successfully while delivering little or no TEL after the source tokens have been transferred. The subsequent referral-credit logic may also use the contract's existing TEL balance, further obscuring the failed output. FeeBuyback should measure TEL before and after the swap, require the balance increase to meet a configured or caller-specified minimum, and validate the expected source amount and route.

Affected Components: the FeeBuyback contract, specifically submit(), the configured aggregator service, the source-token transfer path, and the TEL balance used for referral credits

QA Review: Upon reviewing FeeBuyback.submit in contracts/fee-buyback/FeeBuyback.sol, I confirmed that the alleged missing-output validation exists and can result in asset loss. For non-TEL tokens, the function first calls transferFrom(_safe, address(this), amount), approves the immutable _aggregator, and then executes _aggregator.call{value: msg.value}(swapData). The only swap validation is require(swapResult, "FeeBuyback: swap transaction failed"); there is no check of the TEL balance before and after the call, no minimum-output parameter, and no verification that the expected source amount was consumed through an approved route. Consequently, an aggregator invocation can return success while producing zero or insufficient TEL, leaving the safe’s source tokens spent without obtaining the intended reward asset. The subsequent approval and _referral.increaseClaimableBy call use the contract’s entire TEL balance, which does not establish that the current swap produced any TEL and may even credit zero or residual TEL. Although submit is restricted by onlyOwner, compromise, misconfiguration, or malicious behavior of the authorized service/aggregator still provides a clear exploitable path.
Suggested Mitigation (not independently verified): Record the TEL balance before the swap, require the post-swap increase to meet a caller-supplied or configured minimum output, and validate that the source token transfer and aggregator execution satisfy the expected amount and route.

Stake accounting can exceed actual TEL received for fee-on-transfer or nonstandard TEL

This accounting error can cause recorded stakes to exceed the amount of TEL actually received by the contract. The staking logic records the requested transfer amount without comparing the contract's TEL balance before and after transferFrom(). As a result, it assumes that every configured TEL token transfers the full requested amount.

If a fee-on-transfer, taxed, or otherwise nonstandard token is configured as TEL, a user can receive credit for more stake than the contract holds. The user may later exit for the fully credited amount, leaving the contract unable to honor withdrawals or causing losses to other users. TEL should be restricted to a known standard token, or the module should credit only the measured balance increase and validate the token during initialization.

Affected Components: the StakingModule contract, specifically initialize(), _stake(), and rescueTokens(), together with TEL configuration and stake accounting storage

QA Review: Upon reviewing StakingModule.initialize, _stake, _exit, and rescueTokens, I confirmed a conditional accounting vulnerability for fee-on-transfer or otherwise nonstandard TEL tokens. initialize assigns _telAddress directly to tel without validating its implementation or transfer semantics. In _stake, the requested amount is added to the user checkpoint and _totalStaked before safeTransferFrom executes, with no pre- and post-transfer balance comparison; therefore, if the token credits fewer tokens than requested, the contract records an overstated liability. _exit subsequently attempts to transfer the full recorded amount, which may revert when the contract lacks sufficient balance, or may consume other users’ funds if sufficient surplus exists. rescueTokens also assumes _totalStaked is backed by the token balance and can underflow when the balance is lower, potentially preventing recovery operations. SafeERC20 only validates call success and does not ensure the exact amount was received. The issue is conditional on deployment with an incompatible TEL token or an intentionally nonstandard token, but no source-level guard prevents that configuration.
Suggested Mitigation (not independently verified): Restrict TEL to a known standard token or measure the balance before and after transferFrom and credit only the amount actually received; validate the configured token during initialization.

FeeBuyback ignores ERC20 transfer and approval return values

This accounting error results from ignoring the return values of ERC20 transferFrom() and approve() calls in FeeBuyback.submit(). Tokens that return false instead of reverting can therefore cause funding or allowance setup to fail while execution continues as though the operation succeeded.

The subsequent swap and referral-credit logic may then operate on existing TEL held by FeeBuyback, particularly because the credited amount is derived from the full current balance. This can produce incorrect credits or failed downstream operations. The implementation should use SafeERC20 wrappers, revert whenever transfers or allowance changes fail, and calculate credits from verified balance deltas after successful operations.

Affected Components: the FeeBuyback contract, specifically submit(), including its ERC20 transferFrom(), transfer(), and approve() operations

QA Review: Upon reviewing FeeBuyback.submit in contracts/fee-buyback/FeeBuyback.sol, I confirmed the unchecked ERC20 return-value vulnerability. In both the TEL branch and the general ERC20 branch, transferFrom and approve are invoked directly and their boolean results are discarded. An ERC20 token can therefore return false without reverting, after which execution continues as though funding and allowance setup succeeded. The TEL branch is particularly problematic: it credits _referral with the contract’s entire current TEL balance, not the balance increase attributable to this submission, so a failed transferFrom can cause pre-existing TEL to be assigned to the requested recipient. The general branch similarly proceeds to the aggregator call after a failed transferFrom or approve, potentially operating on existing balances or failing later depending on swap behavior. onlyOwner restricts who can invoke submit, but does not make configured tokens trustworthy or prevent accounting errors caused by false-return tokens. rescueERC20 also ignores transfer results, although it is separate from the stated path. SafeERC20 checks and balance-delta accounting are therefore warranted.
Suggested Mitigation (not independently verified): Replace raw transferFrom, transfer, and approve calls with SafeERC20.safeTransferFrom and forceApprove/safeApprove as appropriate. Revert whenever funding or allowance setup fails, and credit only measured balance deltas after successful operations.
