Executive Summary

The Hound security team conducted this comprehensive audit of the Vader Protocol, reviewing its governance, token, liquidity, conversion, staking, bonding, oracle, and supporting utility components.

The review covered the system architecture, including user and administrator entry points, governance and Timelock controls, VADER/USDV conversion, legacy and V2 pool and router flows, synthetic assets, liquidity positions, staking rewards, bond treasury interactions, oracle dependencies, and external ERC-20 interfaces.

Our team identified multiple confirmed high-impact issues, including ignored liquidity slippage parameters, an unauthorized V2 synthetic-minting path, a USDV daily-limit bypass at cycle rollover, an XVader donation and rounding attack, stale Chainlink price acceptance, and fee-on-transfer accounting weaknesses in V2 pools. We also confirmed incomplete SwapQueue functionality and unsafe zero-address reward-distributor configuration. Overall, the security posture is high risk until access control, pricing validation, token accounting, and incomplete functionality are remediated and comprehensively tested.

System Overview

The Hound team analyzed the Vader Protocol as a collection of governance, token, liquidity, staking, bonding, oracle, and shared-library components. User interactions enter through contracts such as Converter, StakingRewards, VaderRouter, VaderRouterV2, VaderPool, VaderPoolV2, VaderBond, and SwapQueue, while administrator-controlled functionality is mediated through Owned components, GovernorAlpha, Timelock, and configuration setters.

The token and conversion layer consists of Vader, USDV, XVader, Converter, and LinearVesting. Vader and USDV conversion logic depends on LiquidityBasedTWAP pricing, while Converter validates user conversion claims and routes VADER either directly or through vesting. XVader calculates share issuance and redemption from the contract's VADER balance. Our analysis revealed that this balance-based accounting is exposed to direct-donation and integer-rounding manipulation, allowing deposits to receive zero or disproportionately few shares under adverse conditions.

The liquidity layer contains both legacy and V2 implementations. VaderRouter and VaderRouterV2 transfer assets into pool contracts, which calculate reserves, swaps, liquidity positions, LP tokens, and synthetic assets. The routers expose minimum-amount parameters, but the confirmed implementation does not enforce the liquidity-add minimums. In V2, mintSynth accepts arbitrary source and recipient addresses without router-only authorization, and pool transfers use nominal amounts without reconciling actual balance changes, creating material risks for approved-user asset theft and fee-on-transfer or deflationary tokens.

Pricing and reserve-sensitive operations depend on LiquidityBasedTWAP, Chainlink aggregator interfaces, Uniswap pairs, cumulative-price utilities, and VaderMath. The Hound team confirmed that positive but stale Chainlink responses can be accepted because freshness is not enforced, allowing USDV and reserve operations to use outdated valuations. Pool reserve updates do enforce uint112 bounds, preventing the reviewed truncation scenario, but external token behavior and oracle staleness remain important trust-boundary risks.

Staking, bonds, governance, and queue infrastructure provide additional protocol controls and operational flows. StakingRewards uses RewardsDistributionRecipient authorization and balance-backed reward scheduling, while VaderBond interacts with Treasury for bond deposits and payouts. GovernorAlpha includes a quorum requirement, so the reviewed low-participation governance concern was not substantiated. However, SwapQueue contains unimplemented insertion and execution primitives, resulting in silent no-op behavior and zero reimbursement, and rewards distribution can be permanently disabled by setting the distributor to the zero address. These components should be completed or safely disabled, with deployment and governance configuration invariants enforced.

V2 mintSynth lacks router access control and can spend arbitrary approved users' native assets

This access-control vulnerability affects the V2 mintSynth() entry point, which performs an asset transfer and mints synth tokens without restricting calls to the configured router or authenticating the source address. The function accepts arbitrary from and to parameters, uses transferFrom() to move assets from the specified address, and mints the resulting synth tokens to the specified recipient.

If a user has approved the pool to spend native assets, an attacker can call mintSynth() with the victim as from and the attacker as to, causing the victim’s assets to be transferred while the attacker receives the backed synth tokens. This can directly drain approved balances. The function should be restricted to the designated router, use the authenticated caller as the source where appropriate, and validate recipient and authorization relationships.

Affected Components: the VaderPoolV2 contract, specifically mintSynth(), together with the Synth contract’s mint() and burn() functions and the V2 router and synth factory components

QA Review: Upon reviewing VaderPoolV2.mintSynth in contracts/dex-v2/pool/VaderPoolV2.sol, I confirmed that the access-control vulnerability is exploitable. The function is external and protected only by nonReentrant and supportedToken(foreignAsset); unlike mint, swap, and burn, it has no onlyRouter modifier. It calls nativeAsset.safeTransferFrom(from, address(this), nativeDeposit) using the arbitrary from parameter, without requiring from == msg.sender or otherwise authenticating that address. It then obtains or creates the synth through SynthFactory and invokes synth.mint(to, amountSynth). SynthFactory is owned by the pool, and Synth.mint is restricted to that owner, so the pool can successfully mint synth tokens to an attacker-controlled recipient during this call. Consequently, any victim who has directly approved the pool to spend nativeAsset can be targeted by an attacker supplying the victim as from and themselves as to. The router’s access control on other pool functions does not mitigate this independently callable entry point.
Suggested Mitigation (not independently verified): Restrict mintSynth to the configured router and require from == the authenticated user where appropriate, or use msg.sender as the source and avoid arbitrary source addresses. Validate the recipient and add authorization tests covering unauthorized direct calls.

Liquidity add minimum amounts are ignored, enabling slippage and sandwich losses

This slippage-control vulnerability arises because the liquidity-addition routers expose minimum amount parameters but do not enforce them. The legacy and V2 router implementations treat amountAMin and amountBMin as unused and forward only the desired amounts to the pool, without validating the actual assets deposited or liquidity minted.

An attacker can trade or modify liquidity before the transaction executes, changing the pool ratio and causing the user to deposit materially different amounts than expected or receive less liquidity than intended. This enables sandwich and other price-manipulation attacks, potentially resulting in significant user losses. The implementation should validate the actual deposited amounts against the caller’s minimums and enforce a minimum liquidity output.

Affected Components: the legacy VaderRouter and VaderRouterV2 contracts, specifically their addLiquidity() functions, together with the legacy and V2 pool contracts

QA Review: Upon reviewing VaderRouter.addLiquidity and VaderRouterV2.addLiquidity, I confirmed that the slippage controls exposed by the Uniswap V2-compatible interfaces are ignored. In both external overloads, amountAMin and amountBMin are unnamed parameters and are forwarded to overloads that accept only desired amounts, without performing any validation. The legacy router's _addLiquidity function simply returns amountADesired and amountBDesired, transfers both exact amounts to the selected VaderPool, and calls pool.mint(to). Likewise, VaderRouterV2 forwards the desired native and foreign deposits directly to pool.mint, and BasePoolV2._mint transfers precisely those values before calculating liquidity using current reserves and total supply. Consequently, a prior trade or liquidity operation can alter the reserve ratio and reduce the liquidity minted or worsen the economic value of the position, while the caller's specified minimums cannot cause a revert. No minimum-liquidity parameter or post-mint validation exists in either router. The deadline only limits execution time and does not protect against reserve manipulation, so the stated slippage-control weakness is exploitable.
Suggested Mitigation (not independently verified): Calculate the actual deposited amounts and minted liquidity, then require each actual amount to meet its corresponding minimum and require minted liquidity to meet a caller-provided minimum; revert otherwise.

Daily mint limit is bypassed whenever a mint cycle rolls over

This logic error allows the daily mint limit to be bypassed when a new minting cycle begins. The continuing-cycle branch checks the requested amount against dailyLimit, but the cycle-reset branch assigns the requested amount directly to cycleMints without applying the same upper-bound validation.

A user can therefore submit a mint request larger than the configured daily limit immediately after deployment or whenever the cycle timestamp expires. The request can be repeated after each reset, undermining the intended monetary controls and potentially causing excessive USDV and related token issuance. The reset path should enforce uAmount <= dailyLimit or use a unified accounting path that validates the resulting cycle total before minting.

Affected Components: the USDV token contract, specifically mint() and its cycleTimestamp and cycleMints accounting, with the related Vader token minting controls

QA Review: Upon reviewing the USDV.mint function in contracts/tokens/USDV.sol, I confirmed the reported daily-limit logic error. After calculating uAmount from the current VADER price and the user-supplied vAmount, the function enters the reset branch whenever cycleTimestamp is less than or equal to block.timestamp. That branch sets cycleTimestamp to block.timestamp + 24 hours and assigns cycleMints = uAmount without checking uAmount against dailyLimit. The only require enforcing cycleMints <= dailyLimit appears in the continuing-cycle branch, after cycleMints is incremented. Consequently, a caller can submit a mint whose resulting USDV amount exceeds dailyLimit immediately after deployment or after the 24-hour window expires, subject only to ordinary transfer, burn, pricing, and token-balance constraints. The lock modifier does not impose a mint-size restriction, and Vader.mint/burn access control does not enforce USDV's daily limit. The default dailyLimit is also uint256.max, but whenever the owner configures a meaningful lower limit, the rollover path remains exploitable.
Suggested Mitigation (not independently verified): Require uAmount <= dailyLimit in the cycle-reset branch, or use a single accounting path that checks the resulting cycleMints value against dailyLimit before minting.

Swap queue operations are unimplemented and silently return default values

This logic error results from the swap queue’s insertion and execution primitives being declared but left unimplemented. The internal queue functions contain empty bodies, so queue items are not recorded or processed, while Solidity’s default return behavior can make execution appear to complete successfully.

As a result, users or integrating contracts can invoke the queue workflow without queued operations being executed or the expected reimbursement being calculated. This can prevent swaps and other queued work from completing and may leave callers or funds in an unexpected state. The queue should implement and validate insertion and execution, explicitly revert or report failure, and ensure that each queued item is processed exactly once with the correct reimbursement.

Affected Components: the SwapQueue contract, specifically _insertQueue(), _executeQueue(), and executeQueue()

QA Review: Upon reviewing SwapQueue.sol, I confirmed the alleged logic error in the queue primitives. The internal function _insertQueue(uint256) has an empty body and therefore implicitly returns Solidity’s default bool value, false, without modifying the public queue mapping or its linked-list fields. Likewise, _executeQueue() has an empty body and implicitly returns zero. executeQueue() externally invokes _executeQueue(), receives a zero reimbursement, and calls Address.sendValue with that amount, so the transaction can complete successfully while performing no queue processing and transferring no reimbursement. There are no access controls, validation checks, reverts, or other guards that compensate for these missing implementations. Although the supplied contract exposes no public insertion function, meaning the shown code alone does not demonstrate theft or creation of queued entries, any intended workflow or integrating contract relying on these primitives will silently fail: insertion reports failure and execution is a no-op. The issue is therefore a confirmed implementation-level availability and correctness vulnerability, while its ultimate economic impact depends on omitted integration code.
Suggested Mitigation (not independently verified): Implement and test linked-list insertion and execution, explicitly return success or revert on failure, validate queue invariants, and add tests proving that queued items are recorded, processed exactly once, and reimbursed according to the intended policy.

XVader share-price donation attack enables zero-share deposits

This economic-attack vulnerability arises because XVader derives share value directly from the VADER token balance without clearly separating accounted assets from unsolicited transfers or protecting against deposit-rounding effects. Direct token transfers can therefore alter the apparent exchange rate without issuing corresponding shares.

An attacker can make an initial deposit, transfer additional VADER directly to XVader to inflate the share price, and then wait for a victim deposit to round down to very few or zero shares. The attacker may subsequently redeem existing shares against the inflated balance, extracting value from the victim or causing the victim’s deposit to be effectively lost. The implementation should use internal asset accounting or equivalent virtual assets and shares, reject deposits that mint zero shares, and test donation and first-depositor scenarios.

Affected Components: the XVader contract’s share minting and redemption calculations, the Vader token balance used for share-price calculation, and the user deposit and withdrawal flows

QA Review: Upon reviewing XVader.enter and XVader.leave, I confirmed that the alleged donation and rounding vulnerability is exploitable. enter derives the exchange rate from vader.balanceOf(address(this)) and totalSupply(), then computes xVADERToMint using integer division: (_amount * totalShares) / totalVader. There is no internal asset accounting, virtual balance, minimum-share requirement, or check that the minted amount is nonzero. An attacker can obtain initial shares, transfer VADER directly to XVader to inflate totalVader without increasing totalSupply, and then cause a subsequent victim deposit to mint zero or disproportionately few shares when the division rounds down. The victim's VADER remains in the contract, while the attacker can call leave and receive (_shares * vader.balanceOf(address(this))) / totalShares, thereby capturing value attributable to the victim's deposit. The direct transfer is unrestricted by XVader, and leave uses the same raw balance with no protection against donated assets. ERC20 transfer and allowance mechanics do not mitigate this economic flaw.
Suggested Mitigation (not independently verified): Use internal accounted assets rather than raw token balance for pricing, add virtual shares/assets or equivalent minimum-share protections, reject deposits that mint zero shares, and test direct-donation and first-depositor scenarios.

LiquidityBasedTWAP accepts stale or invalid Chainlink responses

This oracle-validation vulnerability results from accepting Chainlink latestRoundData() responses without validating answer positivity, round completeness, or data freshness. LiquidityBasedTWAP uses Chainlink USD feeds as an input, while USDV and VaderReserve rely on the resulting valuation for price-sensitive operations.

If a feed is stalled, incomplete, expired, or returns an invalid answer, an attacker or other caller may execute minting, burning, reserve, or transfer operations using an incorrect price. This can cause mispriced issuance, redemptions, or reserve accounting. The implementation should require a positive answer, nonzero timestamps, a complete round, and a configured maximum data age, with a separately validated fallback or a revert when the feed is invalid.

Affected Components: the LiquidityBasedTWAP contract, its Chainlink price-feed interfaces and retrieval logic, the USDV token’s price-dependent mint and burn paths, and the VaderReserve valuation logic

QA Review: Upon reviewing LiquidityBasedTWAP.getChainlinkPrice and its callers, I confirmed a stale-oracle validation vulnerability. The function invokes latestRoundData(), checks only answeredInRound >= roundID and price > 0, then returns the answer. It does not validate updatedAt, startedAt, roundID != 0, or any maximum age relative to block.timestamp. Consequently, a feed whose latest answer is positive and internally complete but has not been updated for an arbitrary period is still accepted. This value is consumed by _updateVaderPrice, _updateUSDVPrice, _calculateVaderPrice, and _calculateUSDVPrice, which are reached through getVaderPrice and getUSDVPrice. Those public pricing paths are directly used by USDV.mint, USDV.burn, and VaderReserve.reimburseImpermanentLoss, allowing operations to execute against an outdated valuation during a feed outage or stall. The existing positivity and answeredInRound checks mitigate zero, negative, and some incomplete-round responses, but they do not establish freshness. Therefore, the hypothesis is valid, although its claim that all round completeness validation is absent is overstated.
Suggested Mitigation (not independently verified): Require positive answers, nonzero timestamps, complete rounds, and an explicit maximum age before accepting Chainlink data; revert or use a separately validated fallback when the feed is stale or invalid.

V2 pool accounting is vulnerable to fee-on-transfer or deflationary supported tokens

This economic-accounting vulnerability affects V2 pools that support fee-on-transfer or deflationary tokens. The pool and router rely on user-supplied transfer amounts rather than reconciling the actual balance received, and they do not explicitly reject token behaviors that reduce or otherwise modify transferred amounts.

A user can provide a token that transfers less than the nominal amount during liquidity provision or a swap. The pool may then record inflated reserves or credited amounts, causing subsequent pricing, liquidity, synth, or withdrawal calculations to diverge from the assets actually held. The protocol should either reject fee-on-transfer, rebasing, and callback-capable assets during configuration or consistently derive accounting values from pre- and post-transfer balance deltas.

Affected Components: the VaderPoolV2 and VaderRouterV2 contracts, their liquidity-addition and swap transfer paths, the external ERC-20 token boundary, and the VaderMath reserve and liquidity calculations

QA Review: Upon reviewing BasePoolV2._mint, BasePoolV2.swap, BasePoolV2.doubleSwap, VaderPoolV2.mintFungible, and VaderRouterV2._swap, I confirmed that supported fee-on-transfer or deflationary tokens can create an accounting mismatch. Transfers are performed with SafeERC20 using the user-supplied nominal amounts, but no pre/post balance delta is measured. _mint records nativeDeposit and foreignDeposit in reserves, total liquidity calculations, and Position data even if the pool receives less. Likewise, _swap transfers amountIn to the pool and then passes the unchanged nominal value to swap or doubleSwap; BasePoolV2 updates reserves using that value. Consequently, a user can obtain swap output or LP units calculated against more tokens than the pool actually received, while later withdrawals and pricing rely on inflated reserves. Outbound fee-on-transfer behavior is also unhandled: reserves are reduced by the nominal transfer amount although the recipient may receive less, leaving surplus or causing future insolvency; the unrestricted rescue function may expose such surplus. No token-behavior rejection or normalization guard is present in setTokenSupport or the transfer paths.
Suggested Mitigation (not independently verified): Either reject fee-on-transfer, rebasing, and callback-capable assets when configuring supported tokens, or calculate credited amounts from actual balance deltas and use those deltas consistently in reserve, LP, and synth accounting.

medium

Execution reimbursement is always zero and forced ETH cannot be recovered

This availability vulnerability causes execution reimbursement to remain zero because the reimbursement calculation is unimplemented. Since _executeQueue() has an empty body and returns a uint256, callers of executeQueue() receive no calculated reimbursement under Solidity’s default-return semantics.

The contract also lacks an administrator-controlled withdrawal or recovery mechanism for ETH held by its address. ETH sent through an integration path or forcibly transferred using mechanisms such as selfdestruct may therefore become permanently inaccessible, while callers receive no reimbursement for execution. The contract should implement balance-aware reimbursement accounting and provide a narrowly scoped, governance- or owner-protected ETH recovery function.

Affected Components: the SwapQueue contract, specifically executeQueue() and _executeQueue(), including its ETH balance and recovery handling

QA Review: Upon reviewing SwapQueue.sol, particularly executeQueue(), _executeQueue(), and the contract’s complete set of functions, I confirmed that the alleged issue exists in the provided implementation. executeQueue() calls _executeQueue() and forwards its returned value through Address.sendValue(), but _executeQueue() has an empty body and no named return variable or return statement, so the uint256 result defaults to zero. Consequently, callers receive no execution reimbursement regardless of queue activity. The contract also defines no payable receive or fallback function, administrator-controlled withdrawal method, emergency recovery function, or other mechanism to transfer ETH held by the contract. Although ordinary ETH transfers are not accepted, ETH can still be forcibly deposited through mechanisms such as selfdestruct, leaving the balance permanently inaccessible through this contract’s exposed functionality. No access-control or balance-handling logic mitigates either condition. The related _insertQueue() function is also unimplemented, reinforcing that this source is incomplete, but based on the supplied code the zero reimbursement and unrecoverable forced ETH are directly demonstrable.
Suggested Mitigation (not independently verified): Implement the reimbursement calculation and account for the contract balance explicitly; add a narrowly controlled emergency ETH recovery function protected by the intended governance or owner mechanism, and reject or safely handle unsupported funding paths.

Zero-address distributor assignment can permanently disable reward notifications

This availability vulnerability allows the rewards distributor to be set to the zero address because setRewardsDistribution() does not validate the new distributor. StakingRewards uses the configured distributor as the gate for reward-notification operations, so assigning address(0) makes that entry point unusable because no ordinary caller can satisfy the distributor check.

If ownership is later renounced or otherwise becomes unavailable, the invalid configuration may permanently prevent further reward distributions. The setter should reject the zero address, emit an event for every distributor change, and preferably use a two-step update or controlled recovery process before administrative ownership can be relinquished.

Affected Components: the RewardsDistributionRecipient contract, specifically setRewardsDistribution() and onlyRewardsDistribution(), together with the StakingRewards reward-notification entry point and the administrator configuration flow

QA Review: Upon reviewing RewardsDistributionRecipient.setRewardsDistribution and StakingRewards.notifyRewardAmount, I confirmed the described availability weakness. setRewardsDistribution is protected only by onlyOwner and assigns the supplied address directly, without requiring a nonzero address or emitting a change event. The StakingRewards notification entry point is guarded by onlyRewardsDistribution, which requires msg.sender == rewardsDistribution. Once rewardsDistribution is address(0), no practical transaction can satisfy this condition because the zero address cannot originate a call, so notifyRewardAmount becomes permanently unusable unless the owner restores a valid distributor. The StakingRewards constructor also directly accepts and stores a zero _rewardsDistribution, allowing deployment in this broken state. Owned prevents setting owner to zero through its constructor, and this implementation has no explicit renounceOwnership function, so the issue is not automatically permanent after a normal owner action; however, it becomes effectively permanent if the owner key or governing caller is unavailable. Therefore, the hypothesis is a valid conditional availability vulnerability, primarily involving unsafe configuration and lack of recovery safeguards.
Suggested Mitigation (not independently verified): Require the configured distributor address to be nonzero before assignment, emit an event for distributor changes, and use a recovery or two-step distributor update mechanism before ownership can be renounced.

contract Owned {
    address public owner;
    address public nominatedOwner;

    constructor(address _owner) {
        require(_owner != address(0), "Owner address cannot be 0");
        owner = _owner;
        emit OwnerChanged(address(0), _owner);
    }

    function nominateNewOwner(address _owner) external onlyOwner {
        nominatedOwner = _owner;
        emit OwnerNominated(_owner);
    }

    function acceptOwnership() external {
        require(msg.sender == nominatedOwner, "You must be nominated before you can accept ownership");
        emit OwnerChanged(owner, nominatedOwner);
        owner = nominatedOwner;
        nominatedOwner = address(0);
    }

    modifier onlyOwner {
        _onlyOwner();
        _;
    }

    function _onlyOwner() private view {
        require(msg.sender == owner, "Only the contract owner may perform this action");
    }

    event OwnerNominated(address newOwner);
    event OwnerChanged(address oldOwner, address newOwner);
}
