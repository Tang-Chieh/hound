Executive Summary

The Hound security team conducted this comprehensive audit of the Panoptic protocol, reviewing its principal contracts, libraries, interfaces, data types, deployment paths, and trust boundaries.

The review covered the system architecture, including factory-driven pool deployment, collateral tracking, risk assessment, position management, token and metadata components, Uniswap V3 and V4 integrations, oracle and market-state handling, and the flow of assets and control between protocol components and external contracts.

Our review confirmed one high-severity access-control issue in PanopticFactoryV4: pool creation accepts an arbitrary nonzero risk-engine address without authenticating it against an approved implementation or registry. Several additional areas require deployment-specific or code-path validation, including oracle manipulation resistance, packed arithmetic and state validation, token-transfer assumptions, and hash canonicalization. Overall, the architecture contains meaningful safety checks and immutable bindings in several components, but trusted-component configuration and validation remain important security dependencies.

System Overview

The Hound team identified PanopticFactory and PanopticFactoryV4 as the primary deployment entry points. These factories deploy PanopticPool instances, clone CollateralTracker contracts, initialize position-management components, and register deployed pools for later discovery. PanopticFactory integrates with SemiFungiblePositionManager, while PanopticFactoryV4 integrates with SemiFungiblePositionManagerV4 and Uniswap V4-related pool state. FactoryNFT and MetadataStore provide associated token and metadata functionality, with Pointer values used to reference embedded metadata data.

PanopticPool coordinates user-facing position operations, collateral accounting, premium settlement, risk checks, and liquidation-related flows. It calls through IRiskEngine and ISemiFungiblePositionManager, uses Multicall for batching, and relies on InteractionHelper and CollateralTracker for token settlement and collateral updates. CollateralTracker implements ERC20-like share accounting and uses SafeTransferLib across an IERC20Partial trust boundary, making token behavior, transfer success, and accounting consistency important security considerations.

Risk assessment combines RiskEngine calculations with structured values including RiskParameters, PositionBalance, OraclePack, MarketState, PoolData, LiquidityChunk, and LeftRight. Oracle-derived values and market state influence solvency and collateral decisions, while FeesCalc, PanopticMath, Math, and Constants support fee, price, position, and boundary calculations. SemiFungiblePositionManager and SemiFungiblePositionManagerV4 represent positions using TokenId and ERC1155-compatible balances; the V4 path additionally uses V4StateReader to decode packed state from the configured Uniswap V4 pool manager.

Our analysis revealed that the most significant confirmed architectural weakness is the trust placed in a caller-selected risk engine during PanopticFactoryV4 pool creation. A malicious implementation can satisfy the expected interface while returning attacker-controlled risk, margin, solvency, or liquidation results, and the selected address is then embedded into the deployed pool configuration. We also reviewed defensive properties such as immutable external-manager bindings, callback restrictions, conservative oracle checks, low-level token-call handling, and packed data representations. These mechanisms reduce risk in several paths, but the protocol should continue validating trusted implementations, supported collateral assets, oracle inputs, packed-field boundaries, and arithmetic invariants before relying on deployments in production.

Factory accepts an unauthenticated risk-engine address

SUGGESTED MITIGATION: Restrict pool creation to an approved risk-engine registry or bind the factory to an immutable trusted implementation; verify code/interface compatibility and prevent arbitrary risk-engine addresses from being registered for production pools.

Affected Components: factory_v4, risk_engine_interface, risk_engine

QA Review: Upon reviewing the PanopticFactoryV4.deployNewPool function, I confirmed that pool creation accepts any nonzero riskEngine address and performs no allowlist, implementation-address, code-hash, interface, or governance authorization check. Although the subsequent riskEngine.vegoid() call implicitly requires the address to provide a compatible return value, an attacker can deploy a contract implementing the required IRiskEngine methods while returning attacker-controlled values for getRiskParameters, getSolvencyTicks, isAccountSolvent, getMargin, liquidation calculations, and related functions. The selected address is embedded immutably into the PanopticPool and both CollateralTracker clones, so all security-critical pool calculations thereafter trust the attacker’s implementation. The pool is also recorded in s_getPanopticPool and advertised through PoolDeployed, allowing integrators or users that treat factory-registered pools as trusted to interact with it. The mapping’s inclusion of the risk-engine address prevents duplicate-key conflicts but does not establish trust. Therefore, the nonzero check and ABI compatibility implied by vegoid() are insufficient access-control protections.
Suggested Mitigation (not independently verified): Restrict pool creation to an approved risk-engine registry or bind the factory to an immutable trusted implementation; verify code/interface compatibility and prevent arbitrary risk-engine addresses from being registered for production pools.
