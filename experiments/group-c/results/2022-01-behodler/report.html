Executive Summary

The Hound security team conducted this comprehensive audit of the Behodler/Limbo/Flan/DAO protocol, examining its staking, token, governance, liquidity migration, and stabilization components.

The review covered the system architecture, including interactions among Limbo stakers, DAO governance and proposal execution, Flan minting, soul configuration, token proxy migration, Behodler liquidity operations, Uniswap-compatible AMM integrations, and Flan backstop mechanisms.

Our team identified three confirmed security issues in RebaseProxy: a critical mint accounting flaw that can inflate proxy-token supply and drain reserves, a high-severity unchecked transfer failure during redemption, and a medium-severity failure to return calculated mint and redeem amounts. These issues materially weaken accounting integrity and user fund safety, and should be remediated before production use.

System Overview

The Hound team analyzed the Behodler/Limbo/Flan/DAO architecture, centered on Limbo staking and reward flows, Flan issuance, DAO-controlled configuration, and external AMM integrations. Limbo accepts Soul or other configured staked assets, tracks soul and crossing state, and coordinates unstaking, debt adjustment, pending Flan rewards, crossing bonuses, and secondary rewards. FlanLike and FlashGovernanceArbiterLike interfaces provide contract boundaries for token minting and governance-related checks.

Governance is implemented through LimboDAO, Governable, ProposalFactory, and proposal contracts such as UpdateSoulConfigProposal and UpdateMultipleSoulConfigProposal. Governance participants can execute proposals that update Limbo soul configuration, authorize Flan minting, configure asset approvals and proposal-factory settings, and toggle proposal whitelisting. This creates a privileged control path over token issuance and protocol configuration, making proposal authorization, whitelist state, and role separation important security boundaries.

Our analysis revealed a migration path connecting TokenProxyRegistry, RebaseProxy, LimboAddTokenToBehodler, BehodlerLite, and AngbandLike. The migration process redeems proxy tokens, changes burnability, adds liquidity to Behodler, and transfers SCX to Limbo. RebaseProxy is therefore a critical accounting component: openai-codex/gpt-5.6-luna identified that its mint function calculates newly issued proxy tokens from the full post-deposit reserve rather than the caller's deposit, allowing supply inflation and potential reserve extraction.

The system also uses UniswapHelper and UniPairLike to buy and burn Flan, generate stabilization quotes, and route secondary reward operations through an external Uniswap-compatible AMM. FlanBackstop accepts stablecoin input and interacts with PyroTokenLike, UniPairLike, Flan, and PyroFlan to support stabilization and backstop issuance. These integrations introduce external-token and AMM assumptions that must be validated at every transfer and pricing boundary.

Finally, openai-codex/gpt-5.6-luna identified that RebaseProxy.redeem burns proxy tokens before performing an unchecked base-token transfer, and that both mint and redeem declare uint256 return values without returning their calculated amounts. Safe transfer handling, atomic payout guarantees, correct deposit-based mint accounting, and explicit return-value tests are necessary to protect users and downstream integrations.

Mint Calculates Proxy Tokens From Total Reserve Instead of Deposit Amount

This is a critical logic error in the proxy-token minting calculation. The mint() function derives the number of proxy tokens from baseBalance, which represents the contract’s entire reserve, rather than from the amount transferred by the current caller. In addition, the redeem rate is captured before the transfer, causing the calculation to use an inconsistent reserve state. As a result, a small deposit can be treated as though it represents a substantial portion of the existing reserve and supply.

An attacker can exploit this behavior by depositing a negligible amount into an existing pool, receiving an inflated proxy-token balance, and then redeeming those tokens for a disproportionate amount of the underlying base tokens. This can dilute existing holders and allow the attacker to drain reserves. The mint amount should instead be calculated from the caller’s deposited amount using the pre-mint redeem rate, or from the change in reserves, with the rate and supply updated atomically.

Affected Components: the RebaseProxy contract, specifically the mint() function

QA Review: Upon reviewing RebaseProxy.mint in contracts/TokenProxies/RebaseProxy.sol, I confirmed that the vulnerability is exploitable. The function first captures redeemRate() using the contract’s existing base-token balance and total proxy supply, then transfers the caller’s amount into the contract. It subsequently calculates proxy as (baseBalance * ONE) / _redeemRate, where baseBalance is the entire post-transfer reserve rather than the caller’s deposit. If the contract already holds reserve B and has supply S, the pre-transfer rate is approximately B/S, but a small deposit a causes minting of approximately (B+a)/(B/S), or nearly S, instead of the expected a*S/B. The newly minted tokens also dilute the supply and reduce the redeem rate, allowing the attacker to redeem a disproportionate share of the reserve through redeem(), which uses the updated rate. The transferFrom check only ensures payment and does not constrain the minted amount. The zero-supply case is safe, but no guard protects deployments with existing reserves, making this a clear critical accounting flaw.
Suggested Mitigation (not independently verified): Compute the proxy amount from the deposited amount using the pre-mint redeem rate, for example amount * ONE / _redeemRate, or otherwise calculate the change in reserve and update the rate and supply atomically. Add invariant and regression tests ensuring minted proxy value equals only the caller's deposit value.

high

Redeem Ignores ERC20 Transfer Failure

This is a high-severity error-handling vulnerability in the redemption process. The redeem() function burns the caller’s proxy tokens before transferring the corresponding base tokens, but it does not check the boolean result returned by the base token’s transfer() call. If the transfer returns false or otherwise fails without reverting, the transaction can complete successfully even though the user receives no underlying assets.

An affected or maliciously configured base token could therefore cause users to permanently lose their proxy tokens without receiving the expected payout. The transfer must be performed using SafeERC20.safeTransfer(), or its return value must be explicitly required to be true, so that any payout failure reverts the entire transaction, including the preceding token burn.

Affected Components: the RebaseProxy contract, specifically the redeem() function

QA Review: Upon reviewing the redeem function in contracts/TokenProxies/RebaseProxy.sol, I confirmed that the alleged unchecked ERC20 transfer failure is exploitable. The function calculates the payout, executes _burn(msg.sender, amount), and then calls IERC20(baseToken).transfer(to, baseTokens) without checking its boolean return value. Consequently, a base token implementation that returns false rather than reverting can cause the proxy tokens to be irreversibly burned while the recipient receives no base tokens. This is materially different from mint, which explicitly requires transferFrom to return true. Solidity's transaction atomicity does not help when the token reports failure through a false return value, because redeem itself does not revert. A token that reverts would roll back the burn, but ERC20-compatible tokens may legally signal failure by returning false, and the configured base token's behavior is not guarded here. The redeemRate calculation and _burn checks do not validate payout success. Using SafeERC20.safeTransfer or requiring transfer to return true would address the issue.
Suggested Mitigation (not independently verified): Use SafeERC20.safeTransfer, or require IERC20(baseToken).transfer(to, baseTokens) to return true, and ensure the payout failure reverts the entire transaction.

medium

Mint and Redeem Return Zero Despite Declared Return Values

This is a medium-severity interface and accounting logic error in the minting and redemption functions. Although mint() and redeem() declare uint256 return values and calculate the relevant proxy-token and base-token amounts internally, neither function assigns a value to its return variable or explicitly returns the calculated result. Consequently, successful calls report zero to their callers despite changing token balances and contract state.

Integrations that rely on these return values for crediting, reconciliation, or downstream accounting may record incorrect amounts or fail to recognize assets received by a user. The functions should explicitly return the minted proxy-token amount and redeemed base-token amount, and all dependent integrations should consistently use and validate those results.

Affected Components: the RebaseProxy contract, specifically the mint() and redeem() functions

QA Review: Upon reviewing RebaseProxy.mint and RebaseProxy.redeem in contracts/TokenProxies/RebaseProxy.sol, I confirmed that both functions declare a uint256 return value but never assign or explicitly return one. In mint, the contract transfers base tokens, computes the resulting proxy amount in the local variable proxy, and calls _mint(to, proxy), but proxy is not returned. In redeem, it computes baseTokens, burns the requested proxy amount, and transfers the base tokens, but baseTokens is likewise not returned. Consequently, the Solidity return value remains its default zero even though token state changes and assets are transferred. Any integration that relies on these return values for crediting, reconciliation, accounting, or recording received amounts can therefore record zero and potentially create an accounting shortfall or downstream loss. The transferFrom and _burn checks prevent some invalid operations but do not populate the return values or protect dependent callers from incorrect reporting. The vulnerability is therefore clearly present, although its financial impact depends on whether external callers consume these return values.
Suggested Mitigation (not independently verified): Explicitly return the minted proxy amount from mint and the redeemed base-token amount from redeem, and verify all callers use the returned values consistently.
