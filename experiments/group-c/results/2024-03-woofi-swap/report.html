Executive Summary

The Hound security team conducted this comprehensive audit of the WOOFi protocol, reviewing its principal contracts, component interactions, asset flows, oracle dependencies, vault mechanisms, and cross-chain integrations.

The review covered the system architecture, including user-facing swap and deposit entrypoints, WooPP pricing pools, oracle and fee-management components, vault and lending modules, reward infrastructure, access controls, and cross-chain routers and bridge adapters.

Our team identified three confirmed findings and one additional proposed issue, while one availability concern was rejected after review. The confirmed findings include stale-price acceptance caused by global oracle timestamping, stranded excess native currency in WooRouterV3, and insufficient validation of WooCrossFee dependencies. Overall, the protocol has clear modular separation and access-control boundaries, but oracle freshness, payment accounting, and deployment-configuration safeguards require remediation to strengthen asset integrity and operational resilience.

System Overview

The WOOFi architecture is centered on WooRouterV2 and WooRouterV3, which accept user swap requests and forward token transfers and pricing operations to WooPPV2 and WooPPV3. WooPPV2 relies on WooracleV2, while WooPPV3 builds on WooPPBase, reads oracle state, and integrates with lending-related functionality. The routers enforce swap-level parameters such as input amounts, minimum output amounts, and recipient addresses, but the pool and oracle layers remain critical to price integrity.

WooracleV2 stores token pricing, spreads, coefficients, and related state used by WooPPV2 during sell-base, sell-quote, and base-to-base calculations. WooracleV3 instead reads from an AggregatorV3Interface, providing a separate oracle integration path. Our analysis revealed that WooracleV2 uses a global timestamp for feasibility checks, so updating one asset can make another asset's stale price appear current. This creates a direct dependency between administrative oracle updates and the safety of unrelated swap markets.

Fee and authority functions are distributed across WooFeeManager, WooAccessManager, WooRebateManager, and WooVaultManager. WooFeeManager coordinates fee allocation and transfers to rebate and vault components, while WooAccessManager provides authorization boundaries. WooVaultManager calls WOOFiVaultV2, which uses strategy contracts such as BaseStrategy and VoidStrategy. The vault and lending subsystem also includes WooSuperChargerVaultV2 and WooLendingManager, with lending and repayment flows affecting available liquidity and settlement behavior.

The protocol includes reward and data components such as MasterChefWoo, WooSimpleRewarder, and DataProvider, as well as deposit infrastructure through WOOFiDexDepositor and WOOFiDexTestVault. Cross-chain functionality is implemented through WooCrossChainRouterV2, WooCrossChainRouterV3, WooCrossChainRouterV4, WooUsdOFTCrossRouter, and WOOFiDexCrossChainRouter. These components interact with Stargate interfaces, WooUsdOFT, SgInfo, WooCrossFee, and NonceCounter, creating security boundaries around message validation, nonce authorization, fee calculation, and bridged asset handling.

We discovered that WooRouterV3 wraps all supplied native currency even when it exceeds the declared swap amount, leaving the surplus as router-held WETH. We also identified that WooCrossFee accepts oracle, pool, and helper addresses without constructor validation, allowing faulty deployment configuration to cause fee-quote denial of service or integrity problems. Together with the WooracleV2 freshness issue, these findings highlight the need for exact-value accounting, per-asset oracle freshness, and strict dependency validation at deployment and integration boundaries.

Global oracle timestamp allows stale asset prices to remain feasible

An attacker or other market participant can trade the stale token through WooRouterV2 after a different token has been updated by an oracle administrator or automated poster. WooPPV2 and WooRouterV2 may therefore execute swaps using an outdated price, potentially enabling underpriced purchases, overpriced sales, or other value extraction from the pool. Each token should maintain and use its own last-update timestamp for all price, spread, coefficient, and pool-feasibility checks.

Affected Components: the WooracleV2, WooPPV2, and WooRouterV2 contracts, specifically WooracleV2.isWoFeasible(), WooracleV2.postState(), WooracleV2.postStateList(), WooPPV2.tryQuery(), and WooRouterV2.swap()

QA Review: Upon reviewing WooracleV2, I confirmed the alleged oracle-integrity vulnerability. The contract stores a single global `timestamp` variable, while `postPrice`, `postPriceList`, `postSpread`, `postSpreadList`, `postState`, and `postStateList` update that timestamp regardless of which token was modified. In `isWoFeasible`, `price`, and `woState`, feasibility for `infos[base].price` is evaluated using this global timestamp rather than a timestamp associated with `base`. Consequently, if token A's price is old but token B is updated through any administrative posting function, token A can satisfy `block.timestamp <= timestamp + staleDuration` despite not receiving a price update. `WooPPV2` retrieves each token's state in `_tryQuerySellBase`, `_tryQuerySellQuote`, `_tryQueryBaseToBase`, and the swap paths, and enforces only the returned `woFeasible` flag via the calculation helpers. `WooRouterV2` forwards swaps to the pool without an independent freshness check. Chainlink bounds may reject some stale values, but tokens without a usable reference oracle, or stale values still within the bound, remain exploitable.
Suggested Mitigation (not independently verified): Store a last-update timestamp per base token and validate that timestamp in isWoFeasible. Ensure every price, spread, and coefficient update updates only the relevant token timestamp, and use the per-token timestamp in all pool feasibility checks.

WooRouterV3 retains excess native currency as stranded WETH

A user or integrating application that supplies more native currency than the declared input amount can complete the swap while the surplus remains as WETH held by the router. This results in a direct loss of user funds and can also create stranded balances that are not attributable to a completed swap. The router should wrap and transfer exactly fromAmount or explicitly refund msg.value minus fromAmount using a failure-safe transfer mechanism.

Affected Components: the WooRouterV3 and WooPPV3 contracts, specifically the native-input swap branch in WooRouterV3

QA Review: Upon reviewing the native-input branch of WooRouterV3.swap, I confirmed the accounting-integrity issue. When fromToken is the ETH placeholder, the contract only checks that fromAmount <= msg.value, then calls IWETH(WETH).deposit{value: msg.value}(), wrapping the entire payment. It subsequently transfers only fromAmount of WETH to wooPP and executes the swap using fromAmount. There is no transfer, withdrawal, or other refund of msg.value - fromAmount. Consequently, any transaction that supplies excess native currency leaves the surplus as WETH held by the router. The nonReentrant modifier and the receive() restriction do not prevent this condition; they address reentrancy and unsolicited ETH receipts, respectively, rather than enforcing exact payment or returning excess value. The WooPPV3.swap implementation also receives and accounts for only fromAmount, confirming that the surplus is not credited to the user or applied to the swap. Although exploitation generally requires a user or integrator to submit excessive msg.value and the owner can potentially rescue stranded funds, the code clearly permits loss of the surplus without refund.
Suggested Mitigation (not independently verified): Wrap and transfer exactly fromAmount, or explicitly refund msg.value - fromAmount to the caller after the swap while safely handling failed ETH transfers.

medium

Unvalidated external dependency addresses can permanently disable or corrupt fee quoting

A deployment or configuration error, compromised deployment process, or intentionally malicious dependency can cause current-balance and fee functions to revert or return manipulated values. This may disable integrations that rely on fee quotes or compromise fee integrity. The dependencies should be validated during initialization, and any replacement mechanism should be access-controlled, emit events, verify the expected interface and trusted implementation, and reject invalid addresses.

Affected Components: the WooCrossFee contract, specifically the constructor, currentBalance(), ingressFee(), and outgressFee() functions

QA Review: Upon reviewing the WooCrossFee constructor and fee-calculation functions, I confirmed that externally supplied dependencies are accepted without validation. The constructor directly casts _wooracle, _wooPP, and _helper to their expected interfaces and stores them, with no zero-address check, code-existence check, or verification of the expected implementation. currentBalance() then unconditionally calls helper.allBaseTokensLength(), helper.allBaseTokens(), wooracle.price(), wooPP.decimalInfo(), and wooPP.poolSize(). Consequently, a zero address, EOA, incompatible contract, or malicious implementation supplied during deployment can cause ingressFee(), outgressFee(), and direct currentBalance() calls to revert or return manipulated balances and therefore incorrect fee quotes. There are no setters or administrative validation mechanisms that can repair these references after deployment. The issue is not a permissionless post-deployment exploit: exploitation requires a faulty, compromised, or malicious deployment configuration, and trusted deployment controls may reduce practical likelihood. Nevertheless, the code clearly lacks the stated dependency-validation safeguards and provides a direct path to quote denial of service or fee-integrity compromise when those controls fail.
Suggested Mitigation (not independently verified): Reject zero addresses during construction and validate that each dependency supports the expected interface and trusted implementation. Use controlled setters with event emission, access control, and validation if dependency replacement is required; otherwise make the references immutable after verified initialization.
