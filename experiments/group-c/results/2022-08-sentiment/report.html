Executive Summary

The Hound security team conducted this comprehensive audit of the protocol architecture, account infrastructure, oracle system, lending components, and DeFi integration controls.

The review covered high-level protocol boundaries and end-to-end control and data flow, including user interaction with AccountManager and AccountFactory, BeaconProxy account routing and upgrades, Registry and RiskEngine collateral controls, OracleFacade and its pricing adapters, LToken lending pools, and ControllerFacade validation of external DeFi calls.

Our team identified a mixed security posture. Core permission boundaries and administrative allowlists provide important protection, but confirmed material risks remain in oracle freshness and scaling, account upgrade administration, external-protocol calldata validation, recipient binding, Uniswap V3 path validation, recursive oracle configuration, and LP valuation. Several additional concerns were rejected because they depended on privileged misconfiguration or were mitigated by existing target mappings and access controls. The confirmed issues should be prioritized before production deployment or expansion of supported collateral and protocol integrations.

System Overview

The system is organized around AccountManager, AccountFactory, Account, BeaconProxy, and Beacon. AccountFactory creates BeaconProxy account instances, which route delegated execution through Beacon to the Account implementation. Beacon provides implementation upgrades, while Account restricts execution through the account-manager authorization boundary. This upgradeable account architecture allows managed accounts to hold assets and interact with external protocols, but makes proxy-administrator assignment and beacon-change authorization critical security controls.

AccountManager coordinates account lifecycle operations and invokes Account functionality while consulting RiskEngine for collateral and borrowing decisions. RiskEngine reads account balances, LToken debt, Registry configuration, and OracleFacade prices to calculate asset values, health factors, borrowing capacity, and withdrawal eligibility. LToken pools use DefaultRateModel for interest calculations and interact with underlying external assets; the review identified a risk that publicly callable state updates can use temporarily inflated token balances to suppress accrued borrowing interest.

OracleFacade dispatches asset pricing to adapters including ChainlinkOracle, WETHOracle, ATokenOracle, ERC4626Oracle, YTokenOracle, Stable2CurveOracle, UniV2LPOracle, and WeightedBalancerLPOracle. These adapters combine Chainlink feeds, lending-token metadata, vault conversion rates, Yearn accounting values, Curve pool data, Uniswap V2 reserves, and Balancer pool information. The analysis revealed important validation gaps involving stale or incomplete Chainlink rounds, feed decimal assumptions, zero answers, UniV2 LP reserve scaling, and recursive oracle dependencies that can make valuation fail when privileged configuration introduces cycles.

ControllerFacade mediates supported external DeFi interactions through protocol-specific controllers such as AaveV2Controller, AaveV3Controller, UniV2Controller, UniV3Controller, CompoundController, ERC4626Controller, BalancerController, curve controllers, YearnVaultController, and WETHController. ControllerFacade uses target-to-controller mappings configured by an administrator, while each controller parses selectors and calldata before Account execution. Our analysis revealed that several controllers do not bind recipient, owner, sender, or beneficiary fields to the managed Account, and that UniV3 path validation does not consistently validate every token in a route. These gaps can redirect assets or permit unsupported assets to enter account operations when authorized execution is induced with crafted calldata.

Deployment scripts instantiate and connect Registry, AccountManager, AccountFactory, Beacon, RiskEngine, ControllerFacade, OracleFacade, LToken, oracle adapters, and protocol controllers. The deployment and administration model provides meaningful protection against arbitrary users registering controllers or oracle mappings, but it also concentrates risk in privileged configuration. The Hound team recommends enforcing invariant checks during registration and deployment, binding all external-protocol recipients and owners to approved accounts, adding comprehensive oracle freshness and decimal normalization, and introducing recursion, cycle, and upgrade-administrator safeguards.

Stale Chainlink rounds are accepted for collateral valuation

This oracle validation vulnerability accepts stale or incomplete Chainlink rounds for collateral and borrowing calculations. The token and ETH/USD price functions inspect whether the reported answer is negative, but do not verify that the round has been completed, that updatedAt is nonzero, or that the response falls within an approved freshness window. As a result, outdated prices can be passed directly to the risk engine.

An attacker can borrow against collateral while a feed is stale and the market price has materially changed, potentially receiving more debt than the collateral supports. The same issue can distort liquidation and account-health calculations until the feed is updated. The oracle should validate round completeness and enforce a configured maximum data age for every relevant feed.

Affected Components: the ChainlinkOracle contract, specifically the getPrice() and getEthPrice() functions; the Chainlink feeds; the OracleFacade; and the RiskEngine contract, specifically _valueInWei()

QA Review: Upon reviewing ChainlinkOracle.sol:getPrice and getEthPrice, I confirmed that stale or incomplete Chainlink rounds are accepted and used in valuation. Both functions call latestRoundData() but discard roundId, startedAt, updatedAt, and answeredInRound, checking only whether answer is negative. Consequently, a nonnegative answer with updatedAt == 0, an arbitrarily old timestamp, or answeredInRound < roundId is accepted. getPrice computes the token price using the stale token/USD answer and getEthPrice, which applies the same insufficient validation to the ETH/USD feed. OracleFacade.getPrice forwards this value without additional checks, and RiskEngine._valueInWei directly uses it for collateral balances, borrow values, withdrawals, and health-factor calculations. The deployment configures these Chainlink feeds for DAI, WBTC, USDC, and USDT, while ETH/USD is used as the denominator, establishing a clear affected path. Although feed administration is restricted, that does not provide freshness protection during outages or delayed updates; an attacker can transact while stale prices materially misrepresent market value.
Suggested Mitigation (not independently verified): Validate updatedAt against a configured maximum age, require updatedAt != 0, require answeredInRound >= roundId where applicable, and revert when the round is incomplete or stale. Apply equivalent checks to the ETH/USD feed.

Feed decimal mismatch can arbitrarily mis-scale token prices

This oracle scaling vulnerability arises because Chainlink feed decimals are assumed rather than validated or normalized. The price calculation performs raw arithmetic and relies on an undocumented expectation that token feeds use a particular precision, while the interface does not enforce that requirement. A feed using six, eighteen, or another number of decimals can therefore produce a materially mis-scaled token price when combined with the ETH/USD feed.

If an incorrectly configured feed is registered, the risk engine may overvalue or undervalue deposits, borrowing capacity, and withdrawals. An overvalued collateral asset could enable excess borrowing, while an undervalued asset could improperly block valid operations. Feed decimals should be read and normalized to a common scale, or validated against an immutable expected value when feeds are configured.

Affected Components: the ChainlinkOracle contract, specifically getPrice(); the Chainlink feeds; the OracleFacade; the RiskEngine contract, specifically _valueInWei(); and the deployment configuration in Deploy.sol, specifically configureChainLinkOracle()

QA Review: Upon reviewing ChainlinkOracle.sol, RiskEngine.sol, and Deploy.sol, I confirmed that the oracle implementation has an exploitable decimal-normalization flaw when a configured feed uses decimals different from the ETH/USD feed. ChainlinkOracle.getPrice performs `(uint(answer) * 1e18) / getEthPrice()` and only documents, via a comment, that token feeds should return eight decimals; it neither reads feed decimals nor verifies compatibility with the immutable ETH/USD feed. The AggregatorV3Interface also omits a decimals() function. Consequently, a feed with a different precision produces a price scaled by the corresponding power-of-ten factor, and RiskEngine._valueInWei trusts that result for collateral and debt valuation after only normalizing token units. ChainlinkOracle.setFeed accepts any AggregatorV3Interface without validation, and Deploy.configureChainLinkOracle provides no additional check. The deployment’s listed feeds may conventionally use eight decimals, but this is not enforced and future administrative reconfiguration can introduce the mismatch. Exploitation requires an authorized feed-setting or deployment action, rather than an arbitrary permissionless attacker, but the underlying vulnerability is real.
Suggested Mitigation (not independently verified): Read decimals() from both feeds and normalize answers to a common fixed-point scale before division, or enforce and verify an immutable expected decimal value for every configured feed during setFeed.

Spot liquidity can be flash-manipulated to suppress borrow interest

This economic manipulation vulnerability allows the borrow-rate calculation to be influenced by transient spot liquidity. The rate model derives utilization from borrow balances and liquidity, while the LToken integration uses the underlying token's instantaneous balance as the liquidity value. Because updateState() is externally callable, temporary transfers can inflate that balance immediately before interest accrual.

An attacker can supply or borrow flash liquidity, transfer it to the LToken, invoke updateState() while liquidity is artificially high, and remove or repay the temporary funds in the same transaction or block. The inflated denominator reduces utilization and can suppress the interest rate applied to the accrued period, harming lenders and distorting protocol accounting. Accrual should use a protected accounting snapshot, stored or time-weighted liquidity, or another measure that cannot be manipulated around the update call.

Affected Components: the DefaultRateModel contract, specifically getBorrowRatePerSecond(); the LToken contract, specifically updateState() and getBorrows(); and the integrated external lending protocol

QA Review: Upon reviewing LToken.sol, particularly updateState(), getRateFactor(), and the public asset-balance access in getRateFactor(), I confirmed that the alleged economic manipulation is exploitable. updateState() is callable by any address and, when the timestamp changes, calculates accrued interest using rateModel.getBorrowRatePerSecond(asset.balanceOf(address(this)), borrows). DefaultRateModel.sol then computes utilization as borrows divided by liquidity plus borrows, so temporarily transferring underlying tokens to the LToken reduces utilization and the resulting borrow rate. An attacker can supply temporary liquidity, invoke updateState() while that balance is present, and remove or repay the liquidity in the same transaction or block. The only guard is the lastUpdated == block.timestamp check, which prevents repeated accrual within a timestamp but does not prevent the first manipulated update. Other state-changing paths, including beforeDeposit(), beforeWithdraw(), and lendTo(), also invoke the same vulnerable update logic, while no trusted snapshot, minimum holding period, or balance-change sequencing protection exists. Therefore, a flash-loan-funded attacker can suppress interest accrued for the elapsed interval since the prior update.
Suggested Mitigation (not independently verified): Do not base accrual on an unprotected instantaneous token balance. Use a liquidity measure that cannot be temporarily inflated for the accrual call, such as a stored or time-weighted liquidity value, and ensure state updates use a trusted pre-update accounting snapshot. Consider restricting or carefully sequencing balance-changing operations around interest accrual.

Caller-supplied proxy administrator permits unauthorized upgrade control

This access-control vulnerability results from accepting a caller-supplied proxy administrator without binding that address to the account owner or trusted governance. The permissionless account factory passes the supplied administrator into the proxy configuration, and the available validation does not establish that the address is authorized, nonzero, or otherwise suitable to control upgrades.

An attacker can create an account, or cause an integration to create one, with an administrator address controlled by the attacker. If that administrator has proxy upgrade authority, it can install malicious account logic and redirect or control assets held by the proxy. Account creation should be restricted or the administrator should be derived from authenticated ownership or immutable trusted governance, with explicit validation and tests preventing untrusted upgrade control.

Affected Components: the AccountFactory contract and its account-proxy creation logic; the AccountProxy or BeaconProxy configuration; the Account contract; and the associated beacon upgrade mechanism

QA Review: Upon reviewing AccountFactory.create and the proxy administrator logic in BeaconProxy and BaseProxy, I confirmed that the factory accepts an arbitrary caller-supplied administrator without authorization or ownership validation. AccountFactory.create(accountManager) is external and permissionless, and it directly constructs BeaconProxy(beacon, accountManager). BeaconProxy passes that value to BaseProxy._setAdmin, which only rejects address(0); it does not require the administrator to be the account owner, factory, governance, or another trusted address. The resulting administrator can invoke changeBeacon() through the adminOnly modifier and replace the account’s beacon with an attacker-controlled beacon whose implementation contains arbitrary logic. Because the proxy delegates all account calls and may hold assets, this can enable asset theft if an integration creates or funds an account while assigning an attacker-controlled administrator. Beacon ownership does not mitigate this issue because the proxy administrator can change the beacon itself. The supplied code does not demonstrate a victim-facing integration flow, so exploitation against a funded third-party account depends on external usage, but the access-control flaw is directly present.
Suggested Mitigation (not independently verified): Restrict account creation or bind the administrator to the authenticated account owner; reject zero and unsuitable administrator addresses; preferably derive the administrator from immutable trusted governance or the initialized owner rather than accepting an unconstrained caller-supplied value. Add tests proving that an untrusted caller cannot obtain upgrade authority over another user's account.

Aave V3 supply and withdraw recipients are not constrained to the Account

This access-control vulnerability allows Aave V3 supply and withdrawal calls to specify beneficiaries or recipients that are not the managed Account. The controller validates the operation and asset mapping but does not demonstrably bind supply's onBehalfOf field or withdrawal's to field to the Account executing the call.

A caller who can reach the Account or controller execution path may submit supply calldata for an attacker-controlled beneficiary or withdrawal calldata that sends assets to an attacker-controlled address. This can redirect supplied positions or withdrawn funds while preserving otherwise valid protocol parameters. The controller must decode and validate both fields, requiring them to equal the Account unless a separately authorized destination model is explicitly supported, and the facade must not bypass those checks.

Affected Components: the AaveV3Controller contract, specifically supply and withdraw calldata validation; the ControllerFacade; and the Account contract's external protocol execution path

QA Review: Upon reviewing AaveV3Controller.canCall in controller/src/aave/AaveV3Controller.sol, I confirmed that recipient binding is absent for both supported Aave operations. For SUPPLY, the controller decodes only the first argument, asset, from data[4:] and checks the corresponding aToken allowance; it never decodes or validates the third argument, onBehalfOf. For WITHDRAW, it likewise decodes only asset and does not inspect the third argument, to. ControllerFacade.canCall merely forwards calldata to the configured controller and adds no independent validation. Account.exec in protocol/src/core/Account.sol authorizes the accountManager but then forwards arbitrary calldata directly using target.call, without constraining protocol recipient parameters. Consequently, an otherwise authorized execution through this path can supply assets from the Account while crediting aToken ownership to a different address, or withdraw Account-owned aTokens while directing underlying assets to an attacker-controlled recipient. The shown code contains no guard requiring onBehalfOf or to to equal the Account, so the hypothesis is exploitable assuming the normal controller-approved execution path invokes Account.exec.
Suggested Mitigation (not independently verified): Decode and validate onBehalfOf for supply and to for withdraw, requiring each to equal the Account being operated on unless an explicitly approved destination model is intended. Add negative tests for third-party beneficiaries and recipients, and ensure ControllerFacade cannot bypass these checks.

Aave V2 withdrawals are accepted without sufficient authorization checks

This authorization vulnerability affects the Aave V2 withdrawal path, which does not enforce a complete allowlist relationship between the target pool, underlying asset, and corresponding aToken. Unlike the deposit path, which performs an aToken-to-asset mapping, withdrawals are described as always permitted and may therefore reach the controller without equivalent reserve validation.

An attacker may submit a withdrawal through the controller facade using an unapproved asset, pool, or reserve configuration. If the call is forwarded, assets can be transferred out of Aave V2 without satisfying the intended protocol- and asset-level authorization policy. Every withdrawal should validate the canonical pool, confirm the reserve and expected aToken mapping, and reject any unconfigured target or asset.

Affected Components: the AaveV2Controller contract, specifically withdrawal validation; the ControllerFacade; and the Account contract's external protocol call authorization

QA Review: Upon reviewing AaveV2Controller.canCall and ControllerFacade.canCall, I confirmed an authorization gap in the withdrawal validation path. For the WITHDRAW selector, AaveV2Controller decodes only the asset, populates accounting arrays using dataProvider.getReserveTokensAddresses(asset), and unconditionally returns true. It does not verify controllerFacade.isTokenAllowed for the asset or returned aToken, does not validate that the target is the canonical Aave V2 pool, and ignores both the target and useEth parameters. By contrast, the DEPOSIT branch requires the returned aToken to be allowed. ControllerFacade merely dispatches based on controllerFor[target] and adds no independent validation. Account.exec is restricted by accountManagerOnly, which prevents arbitrary external callers from directly executing calls, but it does not correct the missing protocol-specific authorization when the account manager relies on canCall. The underlying Aave pool may revert for nonexistent reserves, and successful withdrawal still requires a corresponding aToken balance, but valid yet unapproved reserves or targets can pass this policy check. Therefore, the claimed withdrawal authorization asymmetry is real, although the practical impact depends on the omitted account-manager execution flow.
Suggested Mitigation (not independently verified): Require every withdrawal to validate the canonical Aave V2 pool, verify that the asset has a registered reserve and expected aToken mapping, and reject assets or targets not present in the configured allowlist.

ERC4626 withdrawal and redemption authorization may permit arbitrary owners and receivers

This access-control vulnerability arises because ERC4626 withdrawal and redemption parameters are not demonstrably bound to an authorized owner and receiver. Both operations accept independent owner and receiver addresses, and the controller validation boundary does not visibly restrict those fields to the managed Account or an approved destination.

An attacker may supply calldata that uses an owner whose shares are accessible to the Account and directs the resulting assets to an attacker-controlled receiver. The same issue can occur when the Account is specified as owner but proceeds are redirected elsewhere. The controller should require the owner to be the executing Account unless a controlled allowance model is implemented, restrict the receiver to the Account or an approved destination, and validate the complete payload before forwarding it.

Affected Components: the ERC4626Controller contract, specifically withdraw() and redeem(); the ControllerFacade; and the Account contract's ERC4626 execution path

QA Review: Upon reviewing the ERC4626Controller.canCall function and the forwarding path through ControllerFacade.canCall and Account.exec, I confirmed that the validator does not enforce authorization of ERC4626 withdrawal or redemption parameters. For REDEEM and WITHDRAW selectors, ERC4626Controller only identifies the vault asset and share token, then returns true; it never decodes or checks the owner or receiver arguments. Consequently, calldata such as withdraw(assets, attacker, account) or redeem(shares, attacker, account) is accepted by the controller, and the more direct case of using the Account as owner while specifying an attacker-controlled receiver is also accepted. Account.exec restricts invocation to accountManagerOnly, but it does not constrain target calldata or the destination encoded within it, so that guard does not provide the missing owner/receiver policy enforcement when the manager executes user-supplied or otherwise attacker-influenced calldata. ERC4626 vault-level authorization may reject arbitrary third-party owners absent allowance, but it does not prevent redirecting assets owned by the Account to an arbitrary receiver. Therefore, the validation boundary is insufficient and the hypothesis is exploitable wherever this controller governs Account execution.
Suggested Mitigation (not independently verified): Require owner to be the executing Account unless a separately authorized allowance model is implemented, and restrict receiver to the Account or an explicitly approved destination. Validate the full calldata before forwarding the call.

Uniswap V3 swap recipient is not constrained to the managed account

This access-control vulnerability permits Uniswap V3 swaps to specify a recipient that is not the managed Account. The swap validator checks selectors, input tokens, and path data, but does not enforce a trusted recipient across supported exact-input, exact-output, or multicall payloads.

An attacker may submit or induce execution of an otherwise permitted swap with an attacker-controlled recipient, causing the Account's assets or swap proceeds to be delivered externally. The controller should decode every supported swap, including nested multicall operations, require the recipient to be the executing Account or an explicitly approved protocol destination, and reject arbitrary recipient values.

Affected Components: the UniV3Controller contract and its swap calldata validation; the ControllerFacade; and the Account contract's validated external protocol execution path

QA Review: Upon reviewing UniV3Controller.canCall and all supported parsing functions, I confirmed that recipient validation is absent. parseExactInputSingle, parseExactOutputSingle, parseExactInput, and parseExactOutput decode the swap parameters but only validate token allowlisting; they never compare params.recipient with the executing Account or another trusted destination. The multicall handlers, including parseExactInputSingleMulticall, parseExactOutputSingleMulticall, parseExactInputMulticall, and parseExactOutputMulticall, likewise decode the swap while ignoring its recipient field. Consequently, a call can pass ControllerFacade.canCall while directing swap output to an arbitrary address. Account.exec restricts execution to accountManagerOnly, which prevents an entirely unauthenticated caller from invoking exec directly, but it does not compensate for the controller’s incomplete policy if the account manager accepts or forwards controller-approved calldata. The source therefore demonstrates a clear fund-redirection condition for any execution path relying on this validation, including all listed swap selectors and supported multicalls.
